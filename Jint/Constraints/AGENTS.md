# Agent instructions: execution constraints

> **Read this when:** You are touching anything that bounds execution — statements, time, memory, recursion depth, cancellation — or a code path those constraints are checked from.
>
> This is one of the co-located instruction files indexed from the repository-root
> [`AGENTS.md`](../../AGENTS.md). Read that first — it carries the build and test commands, the branch to
> target, and the conventions that apply to every file in the repository. Nothing below is
> repeated there.

## Constraints & security

CLR access is disabled by default; enable it with `new Engine(cfg => cfg.AllowClr())`. Execution constraints bound resource use: `options.LimitMemory(4_000_000)`, `options.LimitExecutionTime(TimeSpan.FromSeconds(4))`, `options.LimitStatements(1000)`, or a custom `Constraint` subclass. Read the gotchas in the integration-surface section before relying on any of them.

### What counts as a public contract

These are this area's rows of Jint's public surface. The rule they all obey — **a change to any of it
is a row in [`docs/v5-migration.md`](../../docs/v5-migration.md), written in the same pull request**, even
when it breaks nothing at compile time — and the engine-wide rows are in
[`Jint/AGENTS.md`](../AGENTS.md#what-counts-as-a-public-contract).

| Surface | Location |
| --- | --- |
| `Constraint` + `IsAmortizable` | `Jint/Constraint.cs` |
| `OperationDeadlineConstraint` — public sealed, host-armed `Begin`/`End` budget spanning a whole multi-entry host operation, which the per-entry constraint reset deliberately never rewinds | `Jint/Constraints/OperationDeadlineConstraint.cs` |
| `MemoryLimitConstraint` + `MemoryLimitAccuracy` — per-operation managed-allocation accounting carried across async thread hops, with host-armed `Begin`/`End` for a multi-entry operation | `Jint/Constraints/MemoryLimitConstraint.cs` |
| `Options.Constraints.TimeProvider` (`net8.0`+) — the clock **both** of the engine's own time budgets measure against: `LimitExecutionTime`'s constraint, and `PromiseTimeout`'s blocking drain since [#3406](https://github.com/sebastienros/jint/issues/3406). A frozen clock therefore keeps a blocking `UnwrapIfPromise` or synchronous `Modules.Import` pending until the host advances it, and any new engine-bounded wait takes its deadline from `Engine.GetWaitTimestamp` rather than from `DateTime.UtcNow`. It belongs to the **engine**, not to the `Options` the interval was configured on, and it is **not inherited by a worker** — see below. The web-API timers are *not* on it — they have their own `Options.WebApi.Timers.TimeProvider`, being a WHATWG feature rather than a budget | `Jint/Options.cs`, `Jint/Constraints/ConstraintClock.cs`, `Jint/Engine.cs` |

### Bounding a host-driven sequence

The repository-root [`AGENTS.md`](../../AGENTS.md#gotchas) states the trap: every public entry that runs
script resets the constraints, so `foreach (var row in rows) predicate.Call(row);` hands each element a
fresh budget and a freshly armed deadline, and `Engine.Constraints.Check()` from the host loop does not
close the gap. This is the remedy half. The options are not interchangeable, and three of the four
interact with the tight-loop lane described under [Gotchas](#gotchas) below.

What an embedder must do instead: bound the loop host-side (its own `Stopwatch`, checked between iterations), or move the loop into the script (`rows.forEach(predicate)`) so the whole traversal is one run and one budget. 

The in-engine option for a *budget* is a user-derived `Constraint` whose `Reset()` is a no-op and which stays *exact* (the default `IsAmortizable`, so it is checked on every statement) — which costs the tight-loop lane. 

For the wall-clock half of that budget case there is now an in-box class — `Jint.Constraints.OperationDeadlineConstraint`, which the host brackets with `Begin(budget, token)` / `End()` around the whole operation and whose no-op `Reset()` therefore survives every per-entry reset in between; it observes only a clock and a token, so unlike a hand-written exact budget it declares `IsAmortizable => true` and keeps the tight-loop lane armed, and it throws a real `OperationCanceledException` for the token (Jint's own `ExecutionCanceledException` is a `JintException` and is not one) and the usual `TimeoutException` for the budget. The allocation half has the same shape: `MemoryLimitConstraint.Begin` / `End` brackets one managed-allocation budget across every entry the operation makes, and unlike the deadline it stays *exact*, so it disarms the tight-loop lane for as long as a memory limit is configured at all.

### Gotchas

Each of these cost a real integrator or a real bug. These are the ones that bite in this area; the
rest of the list is split across the files indexed from the repository-root [`AGENTS.md`](../../AGENTS.md).

- **Execution constraints and the interpreter's tight-loop lane.** The lane is disarmed whenever the *exact* (non-amortizable) partition is non-empty, with one exception: a lone `MaxStatementsConstraint` is charged inline and keeps the lane armed. Membership is decided by the constraint's own `public virtual bool IsAmortizable => false`. So a timeout or cancellation keeps the lane, `LimitMemory` disarms it, `MaxStatements` + `LimitMemory` together disarm it, and **any user-derived `Constraint` disarms it unless it overrides `IsAmortizable`**. Only override that for a constraint which merely *observes* external state — never one that counts its own invocations, and never a budget over a quantity that can grow without bound between two checks. Debug mode disarms the lane on its own, whatever the constraints, so never measure this with a debugger attached. `Options.Coverage.Enabled` is the third thing that disarms it, and for the same reason: the hit counters ride along in `Engine.RunPerStatementChecks`, so an engine collecting coverage runs the instrumented path — never measure with it on either.
- **An engine-driven fan-out is one entry, not one per callback — and that is what makes a multi-listener dispatch bounded.** The rule above is about a *host* loop; its mirror image is a loop the engine runs on the host's behalf. `Engine.WebApi.InvokeFetchHandler` firing a `fetch` event at three script-registered listeners brackets `GlobalEventTarget.DispatchEvent` **once** (`Engine.Advanced.WebApi.cs`, `DispatchFetchEvent`), so `ResetConstraints()` runs exactly twice — in and out — with all three listeners in between, and they share one `MaxStatements` allowance, one armed `TimeConstraint` deadline, one `MemoryLimitConstraint` segment and one reset of any host-written `Constraint`. The reason is narrower than it looks and worth knowing before touching either side: a listener is invoked through `ICallable.Call` and so never reaches `ExecuteWithConstraints` at all, which means the bracket is not what *prevents* a per-listener re-arm but what *arms* the dispatch in the first place. Remove it and the dispatch runs against whatever the previous entry left — except for allocation, which `Engine.BeginImplicitMemoryOperation` would still bound, but per listener rather than per dispatch. Any new engine-driven fan-out (another event target the engine dispatches at, a batch callback) inherits the decision: bracket the fan-out, never the element. Pinned from the embedder's side in `Jint.Tests.PublicInterface/WebApiFetchHandlerTests.cs`, by tests that were each confirmed to fail against a build with the bracket moved inside the per-listener loop — the single-listener test that predated them passes that build, which is exactly why counting listeners is the only way to pin this.
- **A public entry that checks constraints without being bracketed does not inherit *no* budget — it inherits the *last* one.** `ExecuteWithConstraints` calls `ResetConstraints()` on the way in and again on the way out for a non-nested entry, so a run *ends* with `TimeConstraint._deadline` armed at `now + interval`. An entry that calls `Constraints.Check()` without going through the bracket therefore measures against a deadline belonging to whatever ran last, however long ago — which is the same mechanism the root [`AGENTS.md`](../../AGENTS.md) records for a host-side `Constraints.Check()`, arriving at a *public API* where no host would look for it. `JsonParser.Parse` was the one instance (sebastienros/jint#3342): the same document on the same engine parsed on a fresh engine, threw `TimeoutException` after an unrelated `Evaluate` and a second's idling, and parsed again from inside a script — because there the surrounding `Evaluate` *was* the bracket. The memory side fails the other way and more quietly: with no entry to attach to, `MemoryLimitConstraint._activeState` is null, `Check()` returns early, and `LimitMemory` bounds nothing. So the rule for any new public entry that observes constraints is that it takes the bracket, and the reason there is exactly one bracket to take — `ExecuteWithConstraints`, whose callback receives its source text as a `ReadOnlySpan<char>` *parameter* rather than closing over it — is that a span cannot be captured by a `Func<T>` and a second copy written for span-taking entries would drift. Pinned from the embedder's side in `Jint.Tests.PublicInterface/HostJsonParseConstraintTests.cs`, including the half a fix breaks: a parse reached from script must go on taking the nested branch, or `JSON.parse` becomes a way for a script to refresh a budget it has already spent.
- **Cancellation is the one thing that does span host calls, because the amortized check *cadence* is engine state.** It is the sibling of the entry above and resolves the other way. A budget must reset per run; a *cadence* must not. `Engine._amortizedConstraintCountdown` therefore lives on the engine and is deliberately **not** rewound by `ResetConstraints()`, so the statements of one short call carry the countdown forward into the next and detection latency stays bounded at `EvaluationContext.AmortizedConstraintCheckInterval` (64) statements *for the engine*, not for one entry. It used to live on `EvaluationContext` and restart at 64 in the constructor, and since every top-level entry builds a fresh context, a callee shorter than 64 statements never reached an amortized check **at all** — which silently defeated `CancellationConstraint.Reset()` being a no-op, the whole point of which is that cancellation survives across entries. A one-statement predicate invoked after `cts.Cancel()` now throws within 64 calls instead of never. Two consequences worth holding on to: this bounds *latency*, never a budget — `TimeoutInterval` is still re-armed per entry and still does not fire across a host loop — and a nested re-entry shares the countdown rather than restarting it, which is correct for a cadence and is what stops a host callback re-entering the engine from resetting the poll interval on every iteration. Any constraint that declares `IsAmortizable => true` inherits all of this, including a user-derived one.
- **`MaxRecursionDepth` counts one function's occurrences, not stack depth — and a tail call's displaced frame keeps counting.** `JintCallStack._statistics` is a multiset of the live stack keyed by `JintFunctionDefinition` identity (`CallStackElementComparer`), so the limit asks "how many times is *this* function on the stack", never "how deep is the stack". Two consequences. A recursion whose every level is a function created for that level — `eval`, `new Function`, a host re-running a script through a callback — repeats no definition and is invisible to the limit however deep it goes; `Options.Constraints.StackOverflowGuard` is the only thing that covers that shape, and no version of Jint has covered it any other way. And `JintCallStack.ReplaceTop` deliberately does **not** discount the frame a proper tail call replaced: the frame is gone, but the activation is not over while `ScriptFunction.ContinueTailCalls` is still on the native stack, so the occurrence is retained and handed back through `ReleaseTailRetention` in that trampoline's `finally`. Discounting it (which is what the code did through 4.16.0) made the limit blind to a recursion that leaves and re-enters the trampoline by a non-tail route — a getter, `new`, a coercion, a Proxy trap, a host callback — because every re-entry pushed the displaced function again at depth zero while the native stack kept growing, and `LimitRecursion` then ended in a process-killing stack overflow instead of a `RecursionDepthOverflowException`. Pinned from both sides in `Jint.Tests.PublicInterface/HostTailCallTests.cs` and `Jint.Tests/Runtime/TailCallOptimizationTests.cs`; the release half has its own test, because without it a loop over one *completed* tail delegation accumulates against the limit.
- **A limit that cannot be reached is not a limit.** This is the single rule for every built-in bound, and each kind of bound obeys it in the way its own kind can. A *constraint* that could never fail is not registered: `LimitStatements(int.MaxValue)`, `LimitMemory(long.MaxValue)`, `LimitExecutionTime(TimeSpan.MaxValue)` and any non-positive value produce exactly the same engine as never calling the method, and additionally *remove* any previously registered constraint of that kind. A *value* setting on `ConstraintOptions` that could never be reached does not arm its check: `MaxRecursionDepth = int.MaxValue` gives the same engine `-1` gives (`EffectiveMaxRecursionDepth` is where that is decided, and through 4.16.0 a saturated depth armed the tracking and then never fired), `MaxArraySize = uint.MaxValue` is the default and means unlimited, and `RegexTimeout` normalises anything .NET's `Regex` could not enforce — non-positive, `TimeSpan.MaxValue`, anything above the `int.MaxValue`-milliseconds ceiling — to `Regex.InfiniteMatchTimeout` (`ConstraintOptions.NormalizeRegexTimeout`, applied at the two points of use so the property still reads back what the host assigned). A host spelling "effectively unlimited" that way has no limit, not a very large one, and a comparison of "with a limit" against "without" written that way compares an engine against itself. What tells the host is `options.ValidateSecurityConfiguration()`, which reads the *configured* value rather than the normalised one so that "you set none" and "you set one that can never fire" stay different diagnostics. When adding a bound, decide which of the two shapes it is and follow the rule; do not invent a third answer (rejecting the value, or clamping it).
- **A budget travels to a second engine; the clock it is measured against does not, and the constraint takes the clock of the engine it is built for.** `LimitExecutionTime` registers a *factory*, and the one thing that replays a factory onto a **different** `Options` instance is `WorkerRequest.CreateDefaultOptions`. While that factory closed over the configuring group, a worker's execution timeout read its **parent's** clock while the `PromiseTimeout` it had just inherited read its own — one engine, two budgets, two clocks (sebastienros/jint#3481). The factory now carries only the interval, and `Engine` binds the very provider `GetWaitTimestamp` reads (`Engine.BindConstraintClocks`), so the two cannot disagree. The classification half is the same decision stated where a settings PR will meet it: `Options.Constraints.TimeProvider` is named in `Options.SecurityPostureNotInherited`, and the reflective pin behind that list now scans **reference-typed** settings too — "reference-typed, therefore host wiring rather than posture" was a rule that let a clock governing two inherited budgets fall outside it entirely. The argument for declining, in one line: script cannot observe the clock (`Date` and `Intl` read `Options.TimeSystem`, `performance.now()` and the timers read `Options.WebApi.Timers.TimeProvider`), so what inheriting it would decide is not what a worker can *see* but whether an inherited budget is still reachable — and a fake clock exists to be stopped, so it is the only answer that can turn a limit into one that cannot fire. Pinned in `Jint.Tests/Runtime/WebApi/WorkerTests.cs`, in both directions, on frozen and self-advancing clocks so no case races the machine.
- **`RegexTimeout` is read from the conversion options, never from the parser's own field.** Jint hangs a `RegexConversionOptions` off `ParserOptions.OnRegExp` carrying both halves of how a pattern is adapted — the compilation mode and the timeout — and resolves `ScriptParsingOptions.RegexTimeout ?? Options.Constraints.RegexTimeout` into it when the script or module is parsed. Acornima's own `ParserOptions.RegexTimeout` sits right beside it and Jint never assigns it, so anything reading *that* gets the parser package's process-wide default. A regex literal was always adapted from the conversion options; every pattern built at run time — `new RegExp`, `RegExp.prototype.compile`, `"x".match("...")`, and the sticky splitter `@@split` rebuilds even from a literal — went through `RegExpConstructor.RegExpInitialize`, which read the field instead, so the host's budget reached one lane and not the other in both directions (sebastienros/jint#3431). Two rules follow for any new construction path. Take the timeout from the same object the compilation mode comes from, falling back to the engine's constraint when no conversion options are in force, which is what `RegExpPrototype.GetCustomEngineTimeout` resolves at match time. And carry that instance onto the parse result whenever the pattern lands on the custom engine, because unlike a .NET `Regex` — which embeds `MatchTimeout` and so cannot be matched under a budget other than the one it was built with — the custom engine has nothing to embed it in and re-reads it per match. **`RegexConversionOptions.Timeout` is nullable, and null is not a default — it is "nobody chose", which only the executing engine can answer** (sebastienros/jint#3442). Preparation is what produces it: there is no engine at prepare time, and resolving it there against Jint's own ten seconds meant a host that had tightened the constraint and adopted `PrepareScript` — the path the README recommends for production — ran at ten seconds while `ValidateSecurityConfiguration` inspected an `Options` that said 400 ms. So every consumer resolves with `conversionOptions.ResolveTimeout(engine)` or the `?? engine.Options.Constraints.RegexTimeout` spelled at the two run-time sites, and a new one must do the same rather than substitute a constant. The literal lane additionally has to key its per-node memo on the resolved value — `JintLiteralExpression.AdaptedRegExp` — because the memo is published onto an AST a `Prepared<Script>` shares, so it must hold a tick count rather than an engine, and the memo of an adaptation that embeds no timeout (a chosen one, or any custom-engine one) is marked as serving every engine so the common case still answers on one comparison. Pinned from the embedder's side in `Jint.Tests.PublicInterface/HostRegexTimeoutTests.cs`, over a matrix of construction shapes that each report which budget fired through `RegexMatchTimeoutException.MatchTimeout` rather than through a clock, and including one prepared script run on two differently-bounded engines in both orders — the order is the whole test, because the hazard is the first engine deciding for the second.
- **`Engine.ConstraintCheckInterval` is calibrated for an array element, and a built-in whose step costs a thousand times more needs its own.** A CLR loop inside one intrinsic crosses no statement boundary, so nothing in `RunPerStatementChecks` is reached while it runs and every bound the host configured is inert for its duration — the property that made sebastienros/jint#3428 unrecoverable, reappearing in a loop that does terminate. `Temporal`'s month walk was the instance (sebastienros/jint#3511): adding months in `chinese`, `dangi` or `hebrew` steps one calendar year at a time, and against a `LimitExecutionTime` of 100 ms it answered two seconds later, against `LimitStatements(10)` 2.2 seconds later, and against a token cancelled from another thread at 210 ms it returned unbothered at three — the largest addition the calendar's range permits ran 43 seconds on one intrinsic call. The remedy is the self-check the bulk array built-ins already do, but the *cadence* is not transferable: ten thousand is right for reading an array element (tens of nanoseconds) and wrong by four orders of magnitude for building a lunisolar year (`NonIsoCalendars.CalendarWalkCheckInterval` is 256 — a dozen new moons and two solstice searches per step, so ten thousand would be a second of latency on a budget a host set to a hundred milliseconds). Take the interval from what one step of *this* loop costs, aim it at a small fraction of the tightest budget a host would plausibly set, and make it a power of two so the cadence is a mask rather than a division. Two consequences are easy to miss. The check charges `MaxStatements` one statement per interval, so the interval is also the resolution at which a statement budget sees the loop — which is what makes `LimitStatements` bound it at all, and why the interval must stay far above what any ordinary call reaches (a year's worth of months is one step). And a walk built out of *other* walks needs a counter of its own: `CalendarDateUntil` measures a month difference by calling `CalendarDateAdd` once per step, and the inner counter restarts on every call, so many short inner walks reach no check between them however long the outer one runs. Pinned from the embedder's side in `Jint.Tests.PublicInterface/HostTemporalCalendarConstraintTests.cs`, every test of which was confirmed to fail against the unmodified loop.
