# Agent instructions: objects, properties and the host-object contract

> **Read this when:** You are touching `ObjectInstance`, a property descriptor, a property-access fast lane, or anything a host subclasses or is verified against.
>
> This is one of the co-located instruction files indexed from the repository-root
> [`AGENTS.md`](../../../AGENTS.md). Read that first — it carries the build and test commands, the branch to
> target, and the conventions that apply to every file in the repository. Nothing below is
> repeated there.

### The subclassing cliff

`ObjectInstance` has two constructors: `protected ObjectInstance(Engine)` and an `internal` one whose parameter types (`ObjectClass`, `InternalTypes`) are themselves internal. A third-party subclass can therefore only reach the protected one, and never carries `InternalTypes.PlainObject` (supplied only through the internal constructor) or `InternalTypes.ShapeMode` (only ever set on the **sealed** `JsObject`). Both are *storage* claims — they let the engine read `_properties` or a shape slot directly — so an object projecting properties lazily from native state could not honour them anyway. The consequence stands: **a host subclass gets no own-property inline caching**, and every own read reaches its `GetOwnProperty`.

What it does get, automatically, is a *semantics* flag. `protected ObjectInstance(Engine)` derives `PropertyAccessSemantics` from the runtime type — overriding `Get` means `Exotic`, not overriding it means `Ordinary` — cached per `Type` process-wide, so the reflection runs once per type however many instances are built. A host declares nothing to be read correctly:

- **Ordinary** (overrides at most `GetOwnProperty`) resolves an own read from a **single** probe: the probe proving the name is not shadowed *is* the read. Such a receiver also reaches the prototype-method inline cache — but only *after* that probe, which re-proves the own miss on every read, so a prototype read costs the same single probe whether the cache is warm or cold.
- **Exotic** (overrides `Get`) routes every read through `Get`, the engine probing nothing itself. This is what a host synthesising values needs, and `Get` is no longer bypassed for names resolving on the prototype.

`SetPropertyAccessSemantics` exists only for the two shapes the rule cannot see: a type overriding `Get` that is nevertheless ordinary (declare `Ordinary` to win the short lane back), and one not overriding `Get` that still is not — e.g. a `GetOwnProperty` unstable across calls for the same name (declare `Exotic`). Call it from the constructor; the last call wins. An `Ordinary` claim is verified on every read whenever host-contract verification is on (below), so running an integration suite that way is the checker. `ArrayLikeObject` (below) is the in-box worked example of the first shape: it seals `Get` as a pass-through purely to stop a subclass going exotic, and then declares `Ordinary` to undo the derivation that sealing triggers.

### Host-contract verification

Several extension points oblige a host to keep two answers consistent, and the engine trusts each of them on the hot path rather than re-verifying. Every one of those obligations has a verifier, and they are all gated on one flag — `HostContractVerification.Enabled` (`Jint/Runtime/HostContractVerification.cs`), a `static readonly bool` the JIT folds:

- **Debug builds**: on, always.
- **Release builds — including the shipped NuGet package**: on when the host sets the AppContext switch `Jint.EnableHostContractVerification` **before its first use of any Jint type**. The flag is read once at type initialization, so setting it later does nothing for the rest of the process.

The point of the switch is reach: the verifiers used to be `[Conditional("DEBUG")]`, and Jint ships Release only, so reaching them meant cloning and building the repository. When adding a verifier, gate it with an explicit `if (HostContractVerification.Enabled)` **at the call site** — `[Conditional]` removes the call and a runtime flag cannot — and report through `HostContractVerification.Fail`, which throws. `Debug.Fail`/`Debug.Assert` are themselves `[Conditional("DEBUG")]` and would report a Release violation into nothing. Reserve them for in-box invariants an embedder can neither violate nor act on (`JintExpression.AssertEvaluationResult`, `FastCallShape`'s leaf-call guard, the pools' validation), which stay compile-time.

**This repository dogfoods that recipe.** `Jint.Tests` and `Jint.Tests.PublicInterface` turn the switch on when the environment variable `JINT_HOST_CONTRACT_VERIFICATION` is `1` or `true`, so the whole host-test surface can be run in the exact configuration an embedder is told to use:

```bash
JINT_HOST_CONTRACT_VERIFICATION=1 dotnet test -c Release Jint.Tests/Jint.Tests.csproj
JINT_HOST_CONTRACT_VERIFICATION=1 dotnet test -c Release Jint.Tests.PublicInterface/Jint.Tests.PublicInterface.csproj
```

The switch is set from a `[ModuleInitializer]` in `Jint.Tests/HostContractVerificationSwitch.cs` (compiled into both projects, and polyfilled on `net472` by the repository's global `PolySharp` reference), because that is the only hook early enough — a fixture, a collection or a class constructor all run after some Jint type has already been touched, and the gate is read once. `HostContractVerificationSwitch.Enabled` is what every verification-aware expectation selects on; `Jint.Tests.Runtime.HostContractVerificationSwitchTests` pins it against Jint's own gate, and `HostContractVerificationTests.TheHarnessSetsTheSwitchEarlyEnoughForJintToObserveIt` proves the same ordering from behaviour alone. The PR workflow runs it as the `linux - host-contract verification` job.

The **default** Release run stays switch-off, deliberately. The probe-count and no-descriptor pins are the regression net for the claim that the gate folds to zero cost when nobody asked for it, and they can only mean that in a run where nobody did. So a test whose expectation differs between the two configurations selects it at runtime from `HostContractVerificationSwitch.Enabled` rather than on `#if DEBUG`, and a test that only makes sense in one of them says so with `[Fact(Skip = "…", SkipUnless = nameof(Verifying))]` (or `nameof(NotVerifying)`) rather than being compiled out. Every verified figure measured so far equals the Debug one — the extra probes are the verifier's own, and nothing else about the two builds differs on these paths.

What is verified: `TryGetOwnPropertyValue` and `ProbeOwnProperty` against `GetOwnProperty`, a declared `PropertyAccessSemantics.Ordinary` against the type's own `Get`, `ArrayLikeObject.HasIndex` against `TryGetIndex`, the named-projection hooks against each other (`HasName` and `NameAt` against `TryGetNamedValue`; a `writable: true` name against the existence of a `TrySetNamedValue` override and the reverse; a `true` from `TryDeleteName` against the name still reading; and, on `ArrayLikeObject`, a projected name that spells an array index or `length`), the builtin-shape probe lane against `GetOwnProperty`, a `PreventExtensions` override that answered `true` against the `Extensible` it left behind, `LazyJsString`'s constructor-declared length against the text its `Materialize()` eventually produces (the one verifier with no out-of-assembly gate, because nothing in the engine derives from that class and the check is one integer comparison on a path that has just done the expensive part), and a typed `AddObjectConverter` registration against what its `TryConvert` actually converts. Each verifier redoes exactly the work the lane it checks exists to avoid, so any figure about descriptors-not-materialized or probes-per-read is a figure from a process with verification **off** — never quote a Debug number as a cost. `Options.Debugger.Enabled` (`Engine._isDebugMode`), which disarms the interpreter's tight-loop lane, is a separate runtime option and has nothing to do with this switch or with the `DEBUG` symbol.

Release probe counts, pinned by `Jint.Tests.PublicInterface/HostObjectProbeCountTests.cs` and `HostObjectSemanticsTests.cs`: for an ordinary host an own hit costs **1**, a name resolving on the direct prototype **1** (warm or cold), and a name absent everywhere **2** — the probe establishing a miss cannot also produce a value, so that read still ends in a `Get` which re-probes before walking the prototype, the one count the derivation did not improve. An exotic host costs **1** either way, and a member-call base like `host.prop.toUpperCase()` costs **1** in both columns. With host-contract verification on (below) those three ordinary rows read **3 / 3 / 4**, the extra probes being the verifier's own; never quote a verifying figure as a cost. The pins are unchanged by the `ProbeOwnProperty` verifier, because none of those hosts overrides it — a host that does pays one descriptor per probe on top, and only while verifying.

The prototype row moved. It used to be **0**: the prototype-method cache answered a warm read without asking the host at all. That was wrong — a host keeps its own-property set outside the engine, so nothing bumps `_propertiesVersion` when a projected member appears, and the cached prototype hit went on shadowing it. The probe is what re-proves the own miss and cannot be removed. What the cache still earns is the second probe and the prototype walk: **1** rather than **2**.

Eight further levers:

- Override `TryGetOwnPropertyValue` so an own read resolves with **no descriptor at all** — the projected value is handed straight over, on the reads the member lane never sees too (computed keys, `Reflect.get`, the base of a member call). It takes every count in the paragraph above to **0** for that host: `true` carries the value, and `false` is an *authoritative* own miss, which is precisely the fact the discarded probe existed to establish, so the prototype-method cache stays honest without it. That authority is the obligation. `false` must mean `GetOwnProperty` would return `Undefined` — never "I could not produce the value", which would make the read resolve on the prototype, or yield `undefined`, for a property that exists. For a key you cannot serve yourself call `base.TryGetOwnPropertyValue`, which *is* the descriptor-driven answer and costs exactly what not overriding would have. Host-contract verification (below) checks both directions on every read. Overriding it is the whole opt-in: the engine derives it from the type, so a host that does not is never asked and its counts do not move.
- Override `ProbeOwnProperty` so existence/enumerability questions (`in`, `hasOwnProperty`, `propertyIsEnumerable`, `Object.keys`/`values`/`entries`, `Object.assign`, spread, `JSON.stringify`) are answered without materializing a descriptor at all. The override must agree with `GetOwnProperty` at the same instant — the engine trusts it on the hot path, and a wrong `Missing` silently drops the key from every enumeration above. Precisely because that failure is so quiet, it now has a verifier: with host-contract verification on, every probe the engine *consumes* is checked against `GetOwnProperty` and the first disagreement throws. The engine reaches the hook through the internal non-virtual `ProbeOwnPropertyChecked`, so a new consumption site must call that, not the virtual; a `base.ProbeOwnProperty` inside an override is not a consumption site. The check runs only for an override declared outside the Jint assembly (in-box ones are covered by in-repo tests, and `ArrayLikeObject`'s through its own `HasIndex` check), decided by a per-`Type` cache mirroring the `PropertyAccessSemantics` derivation. The cost for a host that overrides it: with verification on, an existence question costs one descriptor per probe — the one the probe existed to avoid.
- Where the data is a fixed record, do not subclass at all: `JsObject.Create(engine, layout, values)` and `JsObject.CreateFromEntries` build straight into the hidden-class representation, so objects sharing a layout share one shape and a script reading a batch of them keeps a monomorphic inline cache. `Engine.Advanced.HasSharedShape` lets a test prove the shaping actually happened, since both fall back to the dictionary representation silently; it is a contract, so a host may commit that assertion to its own suite (`GetObjectRepresentation` is the non-contract diagnostic to reach for when a `false` needs explaining).
- Where the object is a **prototype** rather than a record, do not subclass either: `JsObjectShape` declares the members once per process and `Instantiate` creates one such object per engine, in the same shared-layout representation the engine's own intrinsics use. Members materialize per member on first access in that engine, and two properties follow from the representation rather than from anything the host declares — existence and enumerability questions are answered from the layout without creating the member's function (the one exception is the factory form of `PerRealmSlot`, whose flags are not knowable until its factory has run, so it defers), and the object is a valid *holder* for the prototype-method inline cache, which an `ObjectInstance` subclass used as a prototype can never be (below). None of this changes the counts above: those are about the receiver, and a host instance in front of a shaped prototype still pays exactly what its own semantics cost it. Because `Instantiate` returns a type the host cannot derive from, per-prototype bookkeeping goes on the object through `JsObjectShape.SetHostState` / `GetHostState` rather than in a field — an `object?` the engine never reads. It is per *instance*, not per shape, so unlike the delegates and constants inside a shape it **may** be engine-affine, and it dies with the object; a member implementation reaches it by walking up from its receiver, and `GetHostState` answers `null` for a `null` argument so that walk is one expression. Attaching it after creation rather than at `Instantiate` is what lets it hold a reference to the constructor whose `prototype` *is* that object.
- Where the data is a **live indexed collection** (a DOM `NodeList`, a result window, any lazily computed list), derive from `ArrayLikeObject` instead of assembling the property model by hand. A subclass supplies only `uint Length` and `bool TryGetIndex(uint, out JsValue)`; the base class derives the whole coherence matrix from them — the two hooks above, `GetOwnProperty`, both key enumerations, and WebIDL-shaped `Delete`/`DefineOwnProperty` refusals — and two engine lanes key on the *type*: `ArrayOperations` (so `Array.prototype` generics, the array iterator behind `for-of`/spread/`Array.from`/destructuring, and `apply`-spreading cost **one** `TryGetIndex` per element with no key object) and the interpreter's computed-read branch (so `list[i]` costs one `TryGetIndex` with no `Reference` and no descriptor). It is deliberately array-*like*: `Array.isArray` stays `false`, exactly as a browser answers for a `NodeList`. Its elements are deliberately read-only, and **every member it derives is sealed** — `Get`, `GetOwnProperty`, `GetOwnPropertyKeys`, the probe, `Set`, `Delete`, `DefineOwnProperty` — so a host needing to intercept every named read stays on plain `ObjectInstance`, and a host wanting a *named member* declares one through the named-projection hooks below rather than by overriding three of those and keeping them consistent by hand. It is a host subclass like any other, so it is a receiver the caches may serve and never a holder they may trust — a `NodeList.prototype` carrying the collection's methods wants `JsObjectShape` above. A third, optional `protected virtual bool HasIndex(uint)` answers the existence-only questions (`in`, `hasOwnProperty`, the key enumerations, `delete`, the generics' per-element hole test) without projecting an element to discard; its default is exactly `TryGetIndex`-and-discard, so overriding it is pure opt-in, and it carries the same agree-with-`TryGetIndex`-at-the-same-instant obligation the other hooks carry, verified on every probe whenever host-contract verification is on.
- Where the data is a **named record** projected from native state — a settings bag, a row, a document, a live view over a host struct — derive from `NamedPropertyObject`, the sibling of `ArrayLikeObject` for the string-keyed case. It exists because that host used to write **five to eight** mutually-consistent hooks by hand (`GetOwnProperty`, `ProbeOwnProperty`, `GetOwnPropertyKeys`, `TryGetOwnPropertyValue`, `Set`, `Delete`, `DefineOwnProperty`). A subclass now supplies `int NameCount`, `string NameAt(int)` and `bool TryGetNamedValue(string, out JsValue)`, and the base class **seals** all seven of those plus `Get` and `HasProperty`. Because the base overrides `TryGetOwnPropertyValue`, a host reaches the zero-descriptor column above **without knowing it exists**: every read row costs no descriptor and no probe. Symbols and names the projection does not carry stay entirely ordinary, so `Symbol.toStringTag`, `Symbol.iterator` and expandos work as they always did. Sealing `Get` is what makes the `Ordinary` claim its constructor makes true by construction: a host needing to observe reads that resolve on its *prototype* stays on plain `ObjectInstance` — every *own* read is already `TryGetNamedValue`.

- **The named-projection hooks are one set, and both classes publish the same one.** `NamedPropertyObject` declares the first three `abstract`, because a record with no names is not a record; `ArrayLikeObject` declares all eight `virtual` with empty defaults, because a collection with no named members is the common case — and it derives from the runtime type once, cached per `Type` the way `PropertyAccessSemantics` is, whether the type declared any of them at all, so a collection that declared none is never asked. One shared implementation (`NamedProjection.cs`, reached through the internal `INamedProjection` both classes implement explicitly) derives the model from them for both, because two hand-kept copies would reproduce *inside the engine* exactly the incoherence these classes exist to spare a host.

  | hook | default | decides |
  | --- | --- | --- |
  | `NameCount` / `NameAt(int)` | `0` / throws | which names exist, and the enumeration order script sees |
  | `TryGetNamedValue(string, out JsValue)` | carries nothing | the value; `false` is an **authoritative** own miss |
  | `HasName(string)` | ask and discard | existence, with no value produced |
  | `IsNameEnumerable(string)` | `true` | the `enumerable` attribute |
  | `IsNameWritable(string)` | `false` | the `writable` attribute **and** whether assignment routes to the host |
  | `TrySetNamedValue(string, JsValue)` | refuses | one `[[Set]]`; `false` is a refusal, so strict `TypeError` / sloppy no-op |
  | `TryDeleteName(string)` | refuses | one `[[Delete]]`; `false` is a refusal, so `delete` is `false` / strict `TypeError` |

  Three things the defaults buy: a projection that overrides none of the last three is exactly the read-only object the first version of these classes was, so nothing that compiled against it changes; writability is declared **per name** rather than per object, which is what keeps a record with computed fields beside writable ones honest; and `configurable: true` is not a hook at all, because the `[[GetOwnProperty]]` invariants forbid anything else for a projection that may lose a name. That is also why `Object.defineProperty` on a projected name stays refused whatever `IsNameWritable` says — the projection owns all three attributes, so assignment is the write path and a redefinition has nothing to change. `IsNameWritable` answering `true` for a name the projection does *not* yet carry is the WebIDL named-property-setter shape and lets an assignment **create** the name; it runs ahead of the prototype chain and only when the receiver is the object itself. On `ArrayLikeObject` the projection is the *named* half only: canonical array indices and `length` are answered from `Length`/`TryGetIndex` first and a projected name may not spell one.

- **Where the host member is a *callable*, derive from `HostFunction`** (`Jint/Native/HostFunction.cs`) — the function sibling of the two classes above, and the same shape: one abstract member (`Invoke`), everything derived from it sealed. It exists because `Function` *looked* derivable and was not: its only accessible constructor took a `Realm`, and no public member returns one, so `Function.Call` was a `protected abstract` extension point nobody outside the assembly could reach. `Call` is sealed here on purpose, so that what surrounds the body — today, routing an escaping CLR exception through `Options.Interop.ExceptionHandler` exactly as `ClrFunction` does — is a property of the class rather than something each subclass reproduces; both classes share that routing through the `private protected` `Function.ClrExceptionsBubble` / `TranslateClrException` pair, so a new host-callable shape must reach for those rather than growing a third copy. It installs `name` and `length` with the attributes [§10.3](https://tc39.es/ecma262/#sec-built-in-function-objects) gives a built-in (`{ writable: false, enumerable: false, configurable: true }`), which is a deliberate deviation from `ClrFunction`'s non-configurable `length` default — that one is compatibility, this one is new. A host wanting `new` derives from `Constructor` instead; both host-facing constructors take the *principal* realm's `Function.prototype`, never the running realm's, so a callable built after a `ShadowRealm` exists is still a `Function` the surrounding script can recognize.

### When you add a fast lane, decide who can reach it

Several of Jint's fastest lanes are keyed on `internal` type flags or `internal virtual` members that a host type cannot opt into — the member-read inline caches, the built-in fast-call lane, the dense-array lanes. **When adding a new fast lane, decide deliberately whether a host type can reach it, and if not, whether it should be able to.** The `PropertyAccessSemantics` work is the worked example: the lane was originally gated on a storage claim no host could make, and the fix was to split out the weaker *semantics* claim a host could — then derive it, so nobody has to ask. A lane keyed on something only in-box types can assert silently sorts embedders into a slow path they cannot see or escape.

The prototype-method cache's **holder** gate is the second worked example, and it resolved the other way. `VersionWitnessesOwnProperty` refuses a holder carrying `OrdinaryGet`, because for a host subclass that flag stands in for "this object's own-property set lives outside the engine, so no version describes it" — which is why the row above says a host prototype cannot hold an entry. An object in `BuiltinShapeMode` carries the flag too when it reached the protected constructor, but keeps its whole own-property set in engine storage and bumps its version on every change to that set, so it is carved out. A host cannot enter that mode by subclassing — `InitializeBuiltinShape` is `private protected` and `IBuiltinShaped` is internal — but it can *obtain* an object that is in it, from `JsObjectShape.Instantiate`. That is deliberate: the capability is reachable through a factory without the storage protocol being exposed, the same resolution shape as `PropertyAccessSemantics`.

### What counts as a public contract

These are this area's rows of Jint's public surface. The rule they all obey — **a change to any of it
is a row in [`docs/v5-migration.md`](../../../docs/v5-migration.md), written in the same pull request**, even
when it breaks nothing at compile time — and the engine-wide rows are in
[`Jint/AGENTS.md`](../../AGENTS.md#what-counts-as-a-public-contract).

| Surface | Location |
| --- | --- |
| `ObjectInstance` overridable virtuals — `GetOwnProperty`, `HasProperty`, `Delete`, `DefineOwnProperty`, `GetOwnPropertyKeys`, `RemoveOwnProperty`, `PreventExtensions`, `TryGetProperty`, `Initialize`, plus the `protected internal` `TryGetOwnPropertyValue`, `ProbeOwnProperty`, `SetOwnProperty`, `GetPrototypeOf` | `Jint/Native/Object/ObjectInstance.cs` |
| `ObjectInstance.GetOwnProperties` — public, **non-virtual**, derived from `GetOwnPropertyKeys` + `GetOwnProperty` | `Jint/Native/Object/ObjectInstance.cs` |
| `ObjectInstance.DefineOwnPropertyUnchecked` (two overloads) and `DefineOwnDataPropertyUnchecked` | `Jint/Native/Object/ObjectInstance.Unchecked.cs` |
| `ProbeOwnProperty` / `OwnPropertyProbe` | `Jint/Native/Object/` |
| `PropertyAccessSemantics` + `ObjectInstance.SetPropertyAccessSemantics` | `Jint/Native/Object/PropertyAccessSemantics.cs` |
| `ArrayLikeObject` — public abstract class, exactly two abstract members (`Length`, `TryGetIndex`) | `Jint/Native/Object/ArrayLikeObject.cs` |
| `JsObjectLayout` + `JsObjectLayout.CreateBuilder`/`Builder.Add`/`Builder.AddLazy` + `LazySlotFactory`, `JsObject.Create`, `JsObject.CreateFromEntries`, and `Engine.Advanced.HasSharedShape` — the stable predicate that asserts they shaped | `Jint/Native/`, `Jint/Engine.Advanced.cs` |
| `JsObjectShape` + `JsObjectShape.Builder` + `JsObjectShape.Set/GetHostState` | `Jint/Native/JsObjectShape.cs` |

`Get` and `Set` are overridable too, but they are `public override` of `JsValue` virtuals rather than declared on `ObjectInstance`.

### Lazy values: which mechanism owns which storage world

The three lazy mechanisms each own one storage world and are not interchangeable: `JsObjectLayout.Builder.AddLazy` for a member of a fixed-shape **record**, `JsObjectShape` for a member of a **prototype**, [`PropertyDescriptor.CreateLazy`](../../Runtime/Descriptors/AGENTS.md#lazy-values) for a **descriptor** a host stores or returns itself (`SetOwnProperty`/`GetOwnProperty` on a subclass, `DefineOwnPropertyUnchecked` on a dictionary-mode object, a hand-rolled global install). The factory does not change the `DefineOwnPropertyUnchecked` rule in the repository-root [`AGENTS.md`](../../../AGENTS.md) — a string-keyed `DefineOwnPropertyUnchecked` of any raw descriptor still deopts a shape-mode receiver to dictionary — so reaching for it inside a shaped world buys laziness at the cost of the shape.

### Gotchas

Each of these cost a real integrator or a real bug. These are the ones that bite in this area; the
rest of the list is split across the files indexed from the repository-root [`AGENTS.md`](../../../AGENTS.md).

- **An own property kept in a field has to be declared to the key side too.** `GetOwnProperty` answering a name is half a property: the key enumerations read `GetOwnPropertyKeys`, which for an in-box type means overriding it (`JsError`, `IteratorResult`, `JsRegExp`) or the internal `GetInitialOwnStringPropertyKeys` (`Function`'s `length`/`name`/`prototype`, `StringInstance`'s `length`, `JsEvent`'s `isTrusted`). Forgetting the key side ships a property `hasOwnProperty` and `Object.getOwnPropertyDescriptor` both report while `Object.getOwnPropertyNames` and `Reflect.ownKeys` answer an empty list — which is what `f.prototype`'s `constructor` did until [#3455](https://github.com/sebastienros/jint/pull/3455), because it declared itself to `GetOwnProperties` alone. Now that `GetOwnProperties` is derived from the key list, the same omission also hides the property from the CLR conversion path and the debugger, so there is one place to get right instead of two to keep in step.
- **Extensibility is said through `PreventExtensions`, never through the `Extensible` getter.** `Extensible` was `public virtual` over an `internal` setter, which is a shape that cannot be got right: a subclass overriding the getter to a constant keeps the setter, and the setter simply stops feeding the getter. `Object.preventExtensions` then returned the object, `Object.isExtensible` went on answering `true`, strict mode threw nothing and `Object.seal`/`Object.freeze` became no-ops — a `[[PreventExtensions]]` invariant violation no script can detect. Squidex shipped exactly that, twice (`ContentDataObject`, `ContentFieldObject`: `public override bool Extensible => true;`). The getter is non-virtual now, so the shape does not compile; the intent behind it — an object nothing may make non-extensible — is `public override bool PreventExtensions() => false;`, which is an answer `[[PreventExtensions]]` is allowed to give and which makes `Object.preventExtensions` raise a `TypeError` instead of lying. `JsStorage` and a length-tracking `JsTypedArray` are the in-box worked examples. The exotic `[[IsExtensible]]` hook survives as the **internal** `ObjectInstance.IsExtensible()`, for the only two objects that legitimately deviate: a Proxy, which must run the `isExtensible` trap on every read, and a module namespace. The one lie left reachable — `PreventExtensions() => true` without reaching `base` — has a verifier, gated on the override being declared outside the Jint assembly precisely so that reading a Proxy's extensibility (a user trap, with side effects) is never something a verifier does.
- **A global installed *after* construction must invalidate; one installed during it need not.** `Engine.AddLazyGlobal` is the options-time registration's body invoked on a live engine, and the difference is that the live engine's handler trees may already hold a resolved binding for that name — a warmed identifier site keeps the previous descriptor by reference and revalidates it against `GlobalObject._propertiesVersion` alone. `SetProperty` bumps that counter on every path it can take (shared-layout slot replacement, hybrid side-dictionary add, plain dictionary store, deopt fallback), which is exactly why the install goes through it and not through a direct `_properties` write. It correctly leaves `_lexicalMutations` and `_envBindingInjectionEpoch` alone: a global *property* is not a lexical binding and injects nothing into an existing environment. Any future API that installs or replaces a global after construction inherits this; `Jint.Tests/Runtime/LazyGlobalInstallationTests.cs` pins both halves.
