# Agent instructions: writing against the modern BCL

> **Read this when:** You are writing a call site anywhere in `Jint/` that needs an API one of the older target frameworks (`net472`, `netstandard2.0`, `netstandard2.1`) does not have. This file governs the whole assembly, not just this directory.

### Write against the modern BCL, and polyfill downwards

`Jint` multi-targets `net472;netstandard2.0;netstandard2.1;net8.0;net10.0`, so the oldest target decides what compiles. **Write the call site the way you would on .NET 10 anyway, and add the missing API to `Jint/Extensions/Polyfills.cs`** rather than open-coding the old-framework equivalent everywhere or scattering `#if` through the logic.

Use a C# extension member so the call reads identically on every target framework, and guard it with the narrowest symbol for the frameworks that actually lack the API:

```csharp
internal static class DoublePolyfills
{
    extension(double)
    {
#if NETFRAMEWORK || NETSTANDARD2_0
        // double.IsFinite arrived in .NET Core 3.0 / netstandard2.1.
        public static bool IsFinite(double value) => !double.IsNaN(value) && !double.IsInfinity(value);
#endif
    }
}
```

Two things about that shape are load-bearing. The container is **`internal`**: it exists only to host polyfills, and a `public` one both leaks a type whose members differ per target framework and invites `CS0104` in any embedder that has a class of the same name and a `using Jint;`. And there is **one container per receiver type** — a *static* extension member lowers into its containing class with the receiver type erased from the signature, so `int.Parse(ReadOnlySpan<char>, IFormatProvider?)` and `long.Parse(ReadOnlySpan<char>, IFormatProvider?)` differ only by return type and collide with `CS0111` if they share a class. Hence `Int32Polyfills`, `Int64Polyfills`, `DoublePolyfills` are separate; instance extension members have no such constraint and all live on `Polyfills`.

**Mirror the BCL signature exactly, defaults included.** An optional parameter the real API does not have changes overload resolution on the frameworks that *do* have it, so the polyfill quietly stops being one — `int.Parse(ReadOnlySpan<char>, IFormatProvider?)` takes no default on `provider` precisely because the BCL's doesn't.

**A polyfill must match the downlevel API's *behaviour*, not just its signature.** `SortExtensions.StableOrder` is a hand-written merge sort rather than a call to `OrderBy` because LINQ's sort on .NET Framework is a quicksort with no depth limit and no fallback, so an inconsistent comparer — which a JavaScript comparison function is allowed to be — makes it spin forever instead of terminating. Sorting and searching are where downlevel implementations differ most; check them rather than assuming the older framework's version is merely slower.

**Number parsing is the other one, and it is not a polyfill at all — it replaces the BCL everywhere.** .NET Framework's `double.Parse` is not IEEE correctly-rounded: it lands one ULP off for about one in sixty-five 18-digit operands, fails rather than saturating to an infinity on overflow, loses the sign of `-0`, and rejects a leading `+` under the styles the spec lanes passed it. ECMA-262 makes every string-to-number conversion one rounding to the nearest Number, so the answer may not depend on which target framework an embedder loaded — and `parseFloat`, `Number(…)` and `JSON.parse` disagreed with each other on `net472` for the same digits (sebastienros/jint#3532). `NumberParser.TryParseDouble` reads the digits itself and is the only route any of them, `TemporalHelpers`, or the numeric-literal reader takes to a `double` — a literal carrying a fraction, an exponent or more digits than a `ulong` holds reached the *parser's* `double.Parse` and moved for the same reason (sebastienros/jint#3533), so `AstExtensions.NearestDouble` re-reads it here too. Two things about it are deliberate. It is **unconditional** rather than `#if !NET8_0_OR_GREATER`: the `netstandard` assets can be loaded on any runtime, so a guard would still have to compile the managed parser for them, and running it everywhere is what puts it under the whole test262 suite instead of only under the `net472` test leg. And it is **exact rather than approximately right** — a `ulong` fast path and a Clinger scaling by an exactly-representable power of ten settle the common shapes in one rounding, and everything else goes through `BigInteger` division against the rounding boundary. A "close enough" decimal parser is the failure mode here; `Jint.Tests/Runtime/StringToNumberPrecisionTests.cs` holds it to an exact oracle on every target framework.

**And being exact obliges it to be bounded first.** The size of an exact value is the caller's choice, so `parseInt('9'.repeat(1e8))` may not become an allocation — and `parseInt` arrived at the same routine from the other side, having accumulated its digits into a `double` and rounded once per digit, in every radix and on every target framework (sebastienros/jint#3534). An n-digit integer in radix R is at least R^(n-1), so the magnitude follows from the digit count alone: at 311 digits in radix 10 — 1026 in radix 2, 201 in radix 36 — the answer is an infinity whatever the remaining text says and the scan stops there, which caps the widest exact value ever built at about 130 bytes. `TryParseRadixInteger` settles everything under 2^64 in a `ulong`, a radix that is a power of two in a shift with a sticky bit, and every other radix by building the exact integer inside that bound. Anything added here inherits both halves: settle the magnitude from the length, then be exact inside the bound it leaves.

**White space is the third, and it is a classification rather than a parse.** `char.IsWhiteSpace` answers a Unicode question, not an ECMAScript one, and over the whole Basic Multilingual Plane it differs from JavaScript's set on exactly two code points — in both directions, on every target framework: it counts U+0085 NEXT LINE, which is category `Cc` and in neither the `WhiteSpace` nor the `LineTerminator` production, and it does not count U+FEFF ZWNBSP, which is `WhiteSpace`. So `trim`, `parseInt`, `parseFloat`, `Number(…)` and `BigInt(…)` skipped a NEL the parser treats as an ordinary character, and read a lone U+FEFF as `NaN` (sebastienros/jint#3539). `Character.IsJsWhiteSpace` is the one definition every language-level lane reads — the trim halves, the string-to-number lanes, the `\s` character class and `RegExp.escape` — with `IsJsLineTerminator` and `IsJsWhiteSpaceExceptLineTerminator` for the two callers that need the productions apart. Its `Space_Separator` members are **enumerated rather than read from `char.GetUnicodeCategory`**, because .NET Framework carries an older Unicode table than .NET 10 and one definition that moves under an embedder is not one; `Jint.Tests/Runtime/WhiteSpaceDefinitionTests.cs` checks the enumeration against the running framework's table, and sweeps every lane over all 65,536 code units against a set it builds itself. Two sets legitimately are not this one and must not be folded into it: `JsonParser.IsWhiteSpace` is JSON's, which `JSON.parse` defers to ECMA-404 and which is TAB, LF, CR and SP only, and `DefaultTimeSystem` trims host date text with `string.Trim()` because everything the Date Time String Format does not match is implementation-defined anyway.

**A BCL parser reading raw script text is the fourth, and its tolerances are not the styles it was handed.** `long.TryParse`, `int.TryParse` and `uint.TryParse` end a number at a U+0000 and accept however many follow it, the way a C string terminates. That one is the parser's own and no `NumberStyles` flag turns it off — dropping `AllowTrailingWhite` changes nothing — while U+0000 is category `Cc` and in neither white-space production, so it padded a `StringNumericLiteral` on `Number`'s whole-number fast path and an index on `ArrayInstance.ParseArrayIndex`, where `uint.TryParse` took the framework's white space and a leading sign as well (sebastienros/jint#3541). Both now check the last character against what the grammar allows there rather than trusting a style set to say it: an array index ends in a decimal digit, and so does every whole number the fast path exists for — the one legal spelling that does not, `"12."`, falls through and reads the same from the general lane. A lane that hands script text to a BCL parser owes the same guard.

A real member always beats an extension member, so on the frameworks that *do* have the API the BCL implementation is what binds — usually the better one (`double.IsFinite` is a single exponent-bits test where the polyfill is two calls). There is no ambiguity to resolve, and nothing to undo when a target framework is eventually dropped: delete the guarded block and every call site is already correct.

This matters beyond tidiness. Spec algorithms are phrased in terms like "if *x* is finite", so a call site reading `double.IsFinite(x)` can be checked against the spec text at a glance where `!double.IsNaN(x) && !double.IsInfinity(x)` has to be decoded first. `Polyfills.cs` is the single home for these — `string.Join(char, …)` and the `ReadOnlySpan<char>` `Parse`/`TryParse` overloads are already there. Add to it rather than working around it.
