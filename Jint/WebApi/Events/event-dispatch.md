### The algorithm, both lanes, and what a host may override

**The events feature ships the whole DOM dispatch algorithm and no tree to run it over, and both halves are deliberate.** `JsEventTarget.DispatchEvent` (`Jint/WebApi/Events/JsEventTarget.cs`) reads one virtual, `IsNode`, and takes the reduction of the specification's dispatch to the single-item path a tree-less target produces — which is the whole algorithm for an `EventTarget` author code created, not an approximation of it. Every target this engine ships is on that lane, and keeping it there is a promise: it builds no event path, so an `AbortSignal`, a `MessagePort` or a global `error` event allocates exactly what it did before the tree seam existed, which `TreeDispatchTests.ATreeLessDispatchBuildsNoPath` pins structurally rather than by timing. Both passes still run, so `capture` decides *which* pass a listener runs in (a capturing listener on a flat target therefore runs before a non-capturing one whatever order they were registered in), `stopPropagation` ends the dispatch after the current pass while `stopImmediatePropagation` also breaks out of it, each pass walks a clone so a listener added mid-dispatch does not run and one removed does not either, and a `once` listener is removed before it is invoked. **Every listener returns to a microtask checkpoint when the dispatch was entered from a task**, which is WebIDL's *call a user object's operation* running HTML's [clean up after running script](https://html.spec.whatwg.org/multipage/webappapis.html#clean-up-after-running-script), and it is what makes an `XMLHttpRequest`'s `load` and `loadend` — two events fired from one job — order the way a browser orders them ([#3668](https://github.com/sebastienros/jint/issues/3668)). `Engine.CleanUpAfterRunningScript` is the whole of it: the checkpoint is skipped when a *script* started the dispatch (`el.click()`, `target.dispatchEvent(e)`), because then the stack is not empty — and what answers that is the execution-context depth against the depth `RunEventLoopJob` recorded, never `_hostEntryDepth`, which a host `Call` raises with no script on the stack at all. It drains the microtasks at the head of the job queue and stops at the first task, because Jint's one queue holds both and every enqueue site states an `EventLoopJobKind`, with no default, so a new source of deferred work decides rather than inherits. Skipping *past* a task would reorder the one queue, so a microtask behind one still waits for the turn's own drain, which is what every dispatch had before. `Jint.Runtime.EventLoop.WakeJob` exists for that scan: an empty `Action` posted merely to end a park would otherwise stop it, and `Jint.Browser`'s mailbox posts one for the length of every request — so a wake is a shared instance the scan looks past rather than a lambda per call site. **A listener that throws erupts unless the host set a `DiagnosticsSink`**: the specification's "report the exception" (inner invoke step 2.10) needs somewhere to report to, and with a sink that is exactly what happens — the dispatch carries on to the next listener. Without one, swallowing the exception would lose it entirely, so it propagates, the same contract a timer callback has, with the dispatch state unwound in a `finally` either way. Both halves are pinned: `EventTargetTests.AListenerThatThrowsEruptsFromDispatchEvent` for the sinkless engine and `DiagnosticsTests.AThrowingListenerIsReportedAndTheDispatchContinues` for the other, and neither may be "fixed" into agreeing with the other. **A host that has a tree gets `EventDispatch` instead** (`Jint/WebApi/Events/EventDispatch.cs`): the capture, target and bubble phases over a real path, retargeting, `composedPath()` with the closed-tree hiding, and activation behaviour — every step written against seams on `JsEventTarget` (`GetParent`, `TreeParent`, the four shadow queries, `HasActivationBehavior` and its three algorithms) whose defaults say "not in a tree". **Every root that algorithm needs comes from one walk**: `GetRoot()` is asked once for the dispatch target and once for the event's related target, and each path item's root is derived from the step that produced it — a step that stayed inside one node tree has not changed root — so a dispatch is linear in the depth of the tree rather than quadratic in it (#3595). `GetRoot()` is a seam as well, and the only one a host overrides for cost rather than for meaning; an override must answer the target the `TreeParent` walk would have ended on, because the dispatcher steps from tree to tree rather than from node to node. **Every one of those walks is bounded at 10 000 targets** — `JsEventTarget.MaxTreeDepth`, and passing it throws an `InvalidOperationException` naming the host type and the seam (`GetParent`, `TreeParent` or `ShadowHost`) that is answering a cycle (#3596). Nothing else could stop it: the walk is the host's answers rather than script, so no execution constraint counts a step, and a `GetParent` naming a target twice grows the path list until the process runs out. The number is far above any tree an event is dispatched over, the check is one increment per step — a revisit set would allocate on every dispatch to catch the broken host that never comes — and it is deliberately not a `TypeError`: a page must not be able to catch the engine's only report of its host's bug. Nothing in that file knows what a node is; it asks the target, which is what lets the same dispatcher serve Jint's own browser package and, offered upstream, AngleSharp.Js. The one seam a host must not forget is `IsNode`, because it is what selects the lane at all — overriding `GetParent` without it dispatches to the target alone, in silence. Two smaller things worth knowing before editing: `AbortSignal`'s abort algorithms (internal `AddAbortAlgorithm`/`RemoveAbortAlgorithm`) run **before** the `abort` event and are what `fetch` will hang its `CancellationToken` on, which is why the engine cancels that token first of all; and `AbortSignal.timeout()` is an entry on the very `TimerQueue` [`../AGENTS.md`](../AGENTS.md#web-apis) describes, so the events feature creates `Engine._webApi` even when the timers flag is off, and a timeout signal fires only while the engine is pumped.
