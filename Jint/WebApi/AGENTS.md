### Web APIs

`Jint/WebApi/` holds the opt-in WHATWG surface — `console`, `DOMException`, and the timers/encoding/URL/fetch features still landing — with one subfolder and matching namespace per feature (`Console/`, `DomException/`, …). It is deliberately *not* under `Jint/Native/`, which mirrors ECMAScript; these are host APIs guided by WinterTC's Minimum Common Web Platform API, they use the BCL only (no new package dependencies), and their JS-facing types are `internal sealed` and authored with the source generator exactly like the built-ins.

Four conventions hold across the subtree:

- **Whole-file `#if NET8_0_OR_GREATER`.** Every file in `Jint/WebApi/`, the `Options.WebApi.cs` / `Intrinsics.WebApi.cs` partials, and every test file that touches them is wrapped end to end. No `SUPPORTS_` constant is minted for this — those name absent BCL *types*; this is a uniform floor for the whole feature area. The gate is airtight only if `dotnet build -c Release` is run for the **solution**, since `net462`/`netstandard2.0`/`netstandard2.1` are where a leaked reference shows up. Both test suites also compile `net472` on Windows, which is what the test-file wrapping is for.
- **Installed from `Options.Apply`, as lazy globals.** `WebApiRegistration.Apply` runs from the one gated block in `Options.Apply` — the sanctioned conditional-install site, the same one `Interop.Enabled` and `Modules.RegisterRequire` use. `[JsIntrinsicReference]` is not usable here: it is unconditional and would leak into every `ShadowRealm`. Each global is a `LazyPropertyDescriptor<Engine>` installed through `GlobalObject.SetProperty`, exactly as `AddLazyGlobal` does and for its reasons — the version bump that keeps inline caches valid, and the unmaterialized state `RestoreGlobalSnapshot` can revert to. The install is **non-clobbering**: the host's `_configurations` run first and any name the global already owns is left alone, checked with a probe so a host's own lazy global is not materialized just by looking.
- **Only the principal realm.** Nothing outside `Options.Apply` touches a global object, so a `ShadowRealm` never carries these APIs. That diverges from browsers, where they are `[Exposed=*]`; it is a deliberate conservative choice, pinned by a test, and `Host.InitializeShadowRealm` remains the host's door.
- **WebIDL's property attributes, not ECMAScript's.** A regular operation, a static operation, a stringifier, a `toJSON`, an iterable declaration's `entries`/`keys`/`values`/`forEach`, and an iterator prototype's `next`/`return` are all `{ [[Writable]]: true, [[Enumerable]]: true, [[Configurable]]: true }` (<https://webidl.spec.whatwg.org/#es-operations>) — *enumerable*, which is the opposite of ECMA-262's rule for a built-in function property and therefore the opposite of the generator's default. So every `[JsFunction]` under `Jint/WebApi/` spells `Flags = PropertyFlag.ConfigurableEnumerableWritable`, every `[JsAccessor]` spells `Flags = PropertyFlag.Configurable | PropertyFlag.Enumerable` (<https://webidl.spec.whatwg.org/#es-attributes>), a constant is `PropertyFlag.OnlyEnumerable` and a prototype's `constructor` is `PropertyFlag.NonEnumerable`. `Jint.Tests.Runtime.WebApi.WebIdlPropertyAttributeTests` walks every reachable web-API object, classifies every member by its WebIDL member kind and holds it to that kind's attributes, so a member declared with the ECMAScript default fails rather than ships; its doc comment is the table to read when adding one. **This is deliberately not a namespace-scoped generator default**, because the flip is browser-correct only where the object model is: `navigator` and `scheduler` have no interface prototype object, so their members are own properties of the singleton, where an enumerable one would show up in `Object.keys()` and every implementation answers the empty array. Both are exempted by name — with the reason on the host class and an entry in the test's divergence table, which fails on an entry that has stopped diverging.
- **Name order, not IDL order — and that one is a documented divergence, not a rule.** A web-API prototype's own string keys come out in the generator's emission order: constants and `constructor` first, then operations, then attributes, each group sorted by name. [Creating an interface prototype object](https://webidl.spec.whatwg.org/#interface-prototype-object) instead defines regular attributes, then regular operations, then iteration methods, then asynchronous iteration methods, then constants, then `constructor`, each group in IDL declaration order — so `Object.keys(Storage.prototype)` puts `length` last where the algorithm puts it first. Making operations enumerable is what made this reach `Object.keys` and `for...in` rather than only `Reflect.ownKeys`, which is why it was decided rather than discovered (#3271). **It stays as it is, and the argument is WebIDL's own issue tracker**: [whatwg/webidl#432](https://github.com/whatwg/webidl/issues/432) has been open since 2017 recording that no engine implements those steps — "I picked the ordering attributes, constants, operations arbitrarily. Gecko apparently does operations, attributes, constants and Chromium does attributes, constants, operations", neither lexicographical within a group — and the direction it is heading is a lexicographical sort inside each type group, which is exactly what Jint already emits. Node is a fourth order again and puts `constructor` first where the algorithm defines it last, so "matching Node" and "matching WebIDL" are not the same target. Nothing tests the order either: `idlharness` checks membership, attributes, `length`, `name` and the prototype chain and never order, and the two vendored WPT files that do read a prototype's key list sort it before comparing (`streams/readable-streams/general.any.js` and its `async-iterator.any.js` sibling). Reaching the specified order would additionally mean marking which `[JsFunction]`s are iteration methods, splitting `constructor` out of the constants, and holding every host file's C# layout to its interface's IDL order forever with nothing able to check it. `PreserveDeclarationOrder` covers `[JsProperty]` only and is not the lever for this; the reasoning lives beside the sort in `Jint.SourceGenerators/Models.cs`. Nothing under `Jint/Native/` is affected: ECMA-262 clause 18 says nothing about the order a built-in's properties are created in, and V8 does not use the clause order either (`Math` is methods then constants), so there is no order there to diverge from.

**Two globals carry no feature flag at all**, because they are how every other web API reports a failure: `DOMException` and, beside it, `QuotaExceededError` — the one interface WebIDL derives from it (<https://webidl.spec.whatwg.org/#quotaexceedederror>), carrying `quota` and `requested`. Both are installed as soon as any feature is. Three things about the derived one are worth knowing before touching `Jint/WebApi/DomException/`. `JsDomException` is the single **unsealed** type in the subtree, because the derived instance has to answer the very same `name`/`message`/`code` accessors and the brand check in `DomExceptionPrototype` *is* `is JsDomException`. `code` answers **22**, not the 0 the general rule for a derived interface gives, because the name is still in the legacy error-names table marked deprecated — the specification says so itself. And whether an engine-thrown one names its two numbers is decided by the *throwing* algorithm, not by us: `getRandomValues` supplies neither (its step says only "throw a QuotaExceededError", and web-platform-tests asserts `null, null`), while the engine's own caps — timers, sockets, storage, caches — do, because there the cap and the count are exactly what the interface exists to carry. Anything that supplies both owes `requested >= quota`; `QuotaExceededAmounts.Validate` is where a host-supplied pair is held to it.

Feature flags live in `WebApiFeatures`, whose bit layout is fixed ahead of the implementations so a persisted value keeps its meaning — but a flag is **declared only once the feature behind it exists**, so naming one can never compile into an engine that silently lacks it. `WebApiFeatures.Default` is every non-network feature and will never include fetch.

**Timers are the one web API that changed engine infrastructure, and the contract is narrow enough to state in full.** `TimerQueue` (`Jint/WebApi/Timers/TimerQueue.cs`) is a min-heap of due times plus an id map, engine-thread-only and lock-free, reached from `Engine._webApi` (`Jint/Engine.WebApi.cs`) — null on any engine that did not enable the feature, which is what every hot path consults first. Four rules hold it together. **The single job queue is the microtask queue:** `EventLoop.RunAvailableContinuations` promotes exactly *one* due timer, and only when `TryDequeue` has failed, so everything a job queues transitively runs before the next timer is looked at (`Promise.resolve().then` beats `setTimeout(0)`; each timer gets its own checkpoint; an interval cannot starve reactions). Promoting more than one, or promoting before the dequeue, breaks HTML ordering — both mutations are caught by `TimerTests.EachTimerGetsItsOwnMicrotaskCheckpoint`. **There are no background threads:** the clock is `TimeProvider.GetTimestamp`/`GetElapsedTime` and never `TimeProvider.CreateTimer`, so a timer fires on the next pump at or after its due time and an engine nobody pumps never fires one. Since a timer coming due enqueues nothing and therefore wakes nobody, the two wait loops bound themselves by `Engine.TimeUntilNextPumpScheduledWork()` instead — `Engine.DrainEventLoopUntil` clamps its poll interval, and `AwaitPromiseSettlementAsync` takes `EventLoop.WaitForEventAsync(TimeSpan, CancellationToken)`, one `Task.Delay` per idle wait and only while something pends. Both skip the wait entirely when something is due already, *unless* `IsRunningJob` says the queue is unrunnable from here, where an early return would spin hot for the caller's whole timeout. **A restore clears the queue:** `ResetTransientEvaluationState` calls `_webApi?.ResetTransientState()` beside `Modules?.DiscardPendingLoads()`, and each entry additionally carries its registration-time `EventLoopGeneration` into the job it is promoted as, so the generation fence catches one already in flight. **An interval is re-armed before its callback runs**, which is both what the specification says (step 8.2 precedes 8.4) and what stops a throwing callback silently killing it — pinned by `TimerTests.AThrowingCallbackDoesNotStopTheInterval`. Timer callbacks are jobs like promise reactions: same constraint budget, and a throw erupts from whatever is pumping — unless a `DiagnosticsSink` is set, which is what turns that into report-and-continue (see [Diagnostics](#diagnostics-and-reporterror)).

**`Atomics.waitAsync` timeouts ride the same pump, and are the reason `Jint/Engine.Pump.cs` exists.** They are *core* — every target framework, no opt-in — so they cannot live in the net8-only `WebApiEngineState`, and the two hooks the event loop and the wait loops call (`Engine.TryPromoteDueTimerJob`, `Engine.TimeUntilNextPumpScheduledWork`) are declared on every target framework with the conditional compilation inside their bodies, which is what keeps `#if` out of `EventLoop.RunAvailableContinuations`, `DrainEventLoopUntil` and `AwaitPromiseSettlementAsync` entirely. `AtomicsWaiterDeadlines` (`Jint/Native/Atomics/AtomicsWaiterDeadlines.cs`) is a min-heap of `Stopwatch` timestamps hung off `Engine._atomicsWaiterDeadlines`, which is null until the first finite-timeout wait *and again as soon as the last one leaves* — that null is the whole per-job cost. It shares the timers' contract with **one deliberate difference, and the difference is load-bearing: the check runs once per pump iteration, not only when the job queue is exhausted.** test262's `$262.agent.setTimeout` is a promise chain rather than a timer, so a test polling for its own `waitAsync` keeps the queue permanently non-empty and a deadline consulted only at exhaustion would never be consulted at all; `AtomicsWaitAsyncPumpTests.AMicrotaskSpinThatNeverEmptiesTheQueueStillSeesTheTimeout` fails the moment the call is moved into the exhaustion branch. Ordering is untouched by that, because settling only *enqueues* the resolution, behind everything already queued. **The wait's own settle-once flag is the whole race discipline** between the timeout route and an `Atomics.notify` from another agent's thread: the compare-and-swap in `AsyncWaiter.Resolve` decides, the timeout route leaves the waiter list before it claims (so a notify racing it counts the wait as gone rather than waking one about to report timed-out), and the heap reads the flag without synchronization on purpose — a stale `false` costs one extra pass and nothing else. **A restore drops the deadlines and nothing more:** `DiscardAtomicsWaiterDeadlines()` sits beside `_webApi?.ResetTransientState()`, and the waits stay in their blocks' waiter lists exactly as a wait asking for no timeout always has, so what `Atomics.notify` counts does not depend on whether a wait happened to have a timeout; the generation each waiter captured at registration is the fence for a settlement already promoted into a job.

**The events feature is the DOM model minus the tree, and two of its choices are deliberate rather than partial.** `JsEventTarget.DispatchEvent` (`Jint/WebApi/Events/JsEventTarget.cs`) implements the specification's dispatch over the single-item path a tree-less target produces — which is the whole algorithm for an `EventTarget` author code created, not an approximation of it. Both passes still run, so `capture` decides *which* pass a listener runs in (a capturing listener on a flat target therefore runs before a non-capturing one whatever order they were registered in), `stopPropagation` ends the dispatch after the current pass while `stopImmediatePropagation` also breaks out of it, each pass walks a clone so a listener added mid-dispatch does not run and one removed does not either, and a `once` listener is removed before it is invoked. **A listener that throws erupts unless the host set a `DiagnosticsSink`**: the specification's "report the exception" (inner invoke step 2.10) needs somewhere to report to, and with a sink that is exactly what happens — the dispatch carries on to the next listener. Without one, swallowing the exception would lose it entirely, so it propagates, the same contract a timer callback has, with the dispatch state unwound in a `finally` either way. Both halves are pinned: `EventTargetTests.AListenerThatThrowsEruptsFromDispatchEvent` for the sinkless engine and `DiagnosticsTests.AThrowingListenerIsReportedAndTheDispatchContinues` for the other, and neither may be "fixed" into agreeing with the other. Two smaller things worth knowing before editing: `AbortSignal`'s abort algorithms (internal `AddAbortAlgorithm`/`RemoveAbortAlgorithm`) run **before** the `abort` event and are what `fetch` will hang its `CancellationToken` on, which is why the engine cancels that token first of all; and `AbortSignal.timeout()` is an entry on the very `TimerQueue` above, so the events feature creates `Engine._webApi` even when the timers flag is off, and a timeout signal fires only while the engine is pumped.

#### Diagnostics and reportError

**`DiagnosticsSink` (`Jint/WebApi/DiagnosticsSink.cs`) is the one channel for the script errors a host cannot catch**, and the only web-API surface no feature flag governs: `Options.WebApi.Diagnostics.Sink` arms it on its own, so an engine that named no feature at all still gets it (`Options.Apply`'s condition, and the early return at the top of `WebApiRegistration.Apply` that gives such an engine the channel and *no* globals — not even `DOMException`). `WebApiFeatures.Reporting` (`1 << 15`) governs only the `reportError` global, whose whole implementation is HTML's *report an exception* reduced to its last step: this engine's global object is not an `EventTarget`, so nothing is fired, *notHandled* stays true, and "the user agent may report exception to a developer console" is the sink. Without a sink `reportError` is a no-op that never throws; its one failure is WebIDL's arity error for a bare `reportError()`.

Three things to hold on to when touching it. **The sink decides erupt-versus-report, so it is snapshotted at engine build time** into `Engine._webApi.Diagnostics` (and into `TimerQueue.Diagnostics`, so `TimerEntry.Fire` costs a field read and an entry costs no extra reference) — deliberately unlike `ConsoleOptions.Sink`, which is read afresh per emit: a contract that flips mid-script would be unreasonable, and reading `Options.WebApi` from `Engine.OnPromiseRejectionTracker` would force the lazy options group on a *default* engine and mutate shared `Options` from an engine thread. **Only a `JavaScriptException` is ever reported.** All four catch sites (`TimerEntry.Fire`, `JsEventTarget.InvokePass`, `TimerFunctions.InvokeMicrotask` for a `queueMicrotask` callback, and `IdleCallbackQueue.InvokeCallback` for a `requestIdleCallback` one — HTML invokes the microtask with the same WebIDL `"report"` exception behaviour a timer handler gets, and both of the algorithms that reach an idle callback say `"report"` too) key on that type alone with a `when (… is { } diagnostics)` filter, which is precisely the MustPropagate rule stated positively: `ExecutionCanceledException`, `TimeoutException`, `MemoryLimitExceededException`, `StatementsCountOverflowException`, `RecursionDepthOverflowException` and `OperationCanceledException` are all `JintException` but none is a `JavaScriptException`, so a budget still bounds. With no sink there is no `catch` clause at all, which is what keeps the sinkless engine byte-identical. **The promise half is additive and ordered:** `Engine.OnPromiseRejectionTracker` raises `Advanced.PromiseRejectionTracker` first and *then* calls `_webApi?.ReportPromiseRejection`, so the pre-existing public event cannot be perturbed by a sink. It reports at the tracker's cadence, not HTML's — `Promise.reject(e).catch(f)` produces a `RejectionHandled: false` report followed by a `true` one where a browser's deferred checkpoint would raise nothing, which is documented on the property rather than papered over.

**`scheduler.postTask` is deliberately not a fifth site, and the asymmetry is normative rather than an oversight.** Prioritized Task Scheduling (<https://wicg.github.io/scheduling-apis/#schedule-a-posttask-task>) is a WICG draft, not a WHATWG living standard, and it invokes its callback with WebIDL's *other* exception behaviour: "Let callbackResult be the result of invoking callback with « » and `"rethrow"`. If that threw an exception, then reject result with that." The throw therefore belongs in the promise `postTask` handed the caller — which is what `SchedulerTask.Run` already does — and a rejection nobody handles still reaches a sink, as an `UnhandledPromiseRejection` rather than an `UncaughtCallbackError`. Reporting it as a callback error would tell a host about a failure its own `.catch` had already dealt with. `DiagnosticsTests.AThrowingSchedulerTaskRejectsItsPromiseAndIsNeverReportedAsACallbackError` and its public-interface twin are what stop that being “fixed” into symmetry with the four above.
