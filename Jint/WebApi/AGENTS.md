### Citing the living standard

These are owned by WHATWG living standards rather than by ECMA-262, each with its own document and anchor vocabulary: `https://console.spec.whatwg.org/#...`, `https://webidl.spec.whatwg.org/#...` (`#idl-*`, `#es-*`, `#dfn-*`), `https://fetch.spec.whatwg.org/#...` (`#dom-*`, `#concept-*`), `https://dom.spec.whatwg.org/#...`, `https://html.spec.whatwg.org/multipage/...`, `https://encoding.spec.whatwg.org/#...` and `https://url.spec.whatwg.org/#...`. Cite the one that actually defines the thing — `fetch` is WHATWG Fetch, `setTimeout` is HTML, `DOMException` is WebIDL — never MDN. The rest of the citation convention, and the `tc39.es` documents that own everything outside this subtree, are in the repository-root [`AGENTS.md`](../../AGENTS.md).

### Web APIs

`Jint/WebApi/` holds the opt-in WHATWG surface — `console`, `DOMException`, and the timers/encoding/URL/fetch features still landing — with one subfolder and matching namespace per feature (`Console/`, `DomException/`, …). It is deliberately *not* under `Jint/Native/`, which mirrors ECMAScript; these are host APIs guided by WinterTC's Minimum Common Web Platform API, they use the BCL only (no new package dependencies), and their JS-facing types are `internal sealed` and authored with the source generator exactly like the built-ins.

Four conventions hold across the subtree:

- **Whole-file `#if NET8_0_OR_GREATER`.** Every file in `Jint/WebApi/`, the `Options.WebApi.cs` / `Intrinsics.WebApi.cs` partials, and every test file that touches them is wrapped end to end. No `SUPPORTS_` constant is minted for this — those name absent BCL *types*; this is a uniform floor for the whole feature area. The gate is airtight only if `dotnet build -c Release` is run for the **solution**, since `net472`/`netstandard2.0`/`netstandard2.1` are where a leaked reference shows up. Both test suites also compile `net472` on Windows, which is what the test-file wrapping is for.
- **Installed from `Options.Apply`, as lazy globals.** `WebApiRegistration.Apply` runs from the one gated block in `Options.Apply` — the sanctioned conditional-install site, the same one `Interop.Enabled` and `Modules.RegisterRequire` use. `[JsIntrinsicReference]` is not usable here: it is unconditional and would leak into every `ShadowRealm`. Each global is a `LazyPropertyDescriptor<Engine>` installed through `GlobalObject.SetProperty`, exactly as `AddLazyGlobal` does and for its reasons — the version bump that keeps inline caches valid, and the unmaterialized state `RestoreGlobalSnapshot` can revert to. The install is **non-clobbering**: the host's `_configurations` run first and any name the global already owns is left alone, checked with a probe so a host's own lazy global is not materialized just by looking.
- **Only the principal realm.** Nothing outside `Options.Apply` touches a global object, so a `ShadowRealm` never carries these APIs. That diverges from browsers, where they are `[Exposed=*]`; it is a deliberate conservative choice, pinned by a test, and `Host.InitializeShadowRealm` remains the host's door.
- **WebIDL's property attributes, not ECMAScript's.** A regular operation, a static operation, a stringifier, a `toJSON`, an iterable declaration's `entries`/`keys`/`values`/`forEach`, and an iterator prototype's `next`/`return` are all `{ [[Writable]]: true, [[Enumerable]]: true, [[Configurable]]: true }` (<https://webidl.spec.whatwg.org/#es-operations>) — *enumerable*, which is the opposite of ECMA-262's rule for a built-in function property and therefore the opposite of the generator's default. So every `[JsFunction]` under `Jint/WebApi/` spells `Flags = PropertyFlag.ConfigurableEnumerableWritable`, every `[JsAccessor]` spells `Flags = PropertyFlag.Configurable | PropertyFlag.Enumerable` (<https://webidl.spec.whatwg.org/#es-attributes>), a constant is `PropertyFlag.OnlyEnumerable` and a prototype's `constructor` is `PropertyFlag.NonEnumerable`. `Jint.Tests.Runtime.WebApi.WebIdlPropertyAttributeTests` walks every reachable web-API object, classifies every member by its WebIDL member kind and holds it to that kind's attributes, so a member declared with the ECMAScript default fails rather than ships; its doc comment is the table to read when adding one. **This is deliberately not a namespace-scoped generator default**, because the flip is browser-correct only where the object model is: `navigator` and `scheduler` have no interface prototype object, so their members are own properties of the singleton, where an enumerable one would show up in `Object.keys()` and every implementation answers the empty array. Both are exempted by name — with the reason on the host class and an entry in the test's divergence table, which fails on an entry that has stopped diverging.
- **Name order, not IDL order — and that one is a documented divergence, not a rule.** A web-API prototype's own string keys come out in the generator's emission order: constants and `constructor` first, then operations, then attributes, each group sorted by name. [Creating an interface prototype object](https://webidl.spec.whatwg.org/#interface-prototype-object) instead defines regular attributes, then regular operations, then iteration methods, then asynchronous iteration methods, then constants, then `constructor`, each group in IDL declaration order — so `Object.keys(Storage.prototype)` puts `length` last where the algorithm puts it first. Making operations enumerable is what made this reach `Object.keys` and `for...in` rather than only `Reflect.ownKeys`, which is why it was decided rather than discovered (#3271). **It stays as it is, and the argument is WebIDL's own issue tracker**: [whatwg/webidl#432](https://github.com/whatwg/webidl/issues/432) has been open since 2017 recording that no engine implements those steps — "I picked the ordering attributes, constants, operations arbitrarily. Gecko apparently does operations, attributes, constants and Chromium does attributes, constants, operations", neither lexicographical within a group — and the direction it is heading is a lexicographical sort inside each type group, which is exactly what Jint already emits. Node is a fourth order again and puts `constructor` first where the algorithm defines it last, so "matching Node" and "matching WebIDL" are not the same target. Nothing tests the order either: `idlharness` checks membership, attributes, `length`, `name` and the prototype chain and never order, and the two vendored WPT files that do read a prototype's key list sort it before comparing (`streams/readable-streams/general.any.js` and its `async-iterator.any.js` sibling). Reaching the specified order would additionally mean marking which `[JsFunction]`s are iteration methods, splitting `constructor` out of the constants, and holding every host file's C# layout to its interface's IDL order forever with nothing able to check it. `PreserveDeclarationOrder` covers `[JsProperty]` only and is not the lever for this; the reasoning lives beside the sort in `Jint.SourceGenerators/Models.cs`. Nothing under `Jint/Native/` is affected: ECMA-262 clause 18 says nothing about the order a built-in's properties are created in, and V8 does not use the clause order either (`Math` is methods then constants), so there is no order there to diverge from.

**Two globals carry no feature flag at all**, because they are how every other web API reports a failure: `DOMException` and, beside it, `QuotaExceededError` — the one interface WebIDL derives from it (<https://webidl.spec.whatwg.org/#quotaexceedederror>), carrying `quota` and `requested`. Both are installed as soon as any feature is. Three things about the derived one are worth knowing before touching `Jint/WebApi/DomException/`. `JsDomException` is the single **unsealed** type in the subtree, because the derived instance has to answer the very same `name`/`message`/`code` accessors and the brand check in `DomExceptionPrototype` *is* `is JsDomException`. `code` answers **22**, not the 0 the general rule for a derived interface gives, because the name is still in the legacy error-names table marked deprecated — the specification says so itself. And whether an engine-thrown one names its two numbers is decided by the *throwing* algorithm, not by us: `getRandomValues` supplies neither (its step says only "throw a QuotaExceededError", and web-platform-tests asserts `null, null`), while the engine's own caps — timers, sockets, storage, caches — do, because there the cap and the count are exactly what the interface exists to carry. Anything that supplies both owes `requested >= quota`; `QuotaExceededAmounts.Validate` is where a host-supplied pair is held to it.

Feature flags live in `WebApiFeatures`, whose bit layout is fixed ahead of the implementations so a persisted value keeps its meaning — but a flag is **declared only once the feature behind it exists**, so naming one can never compile into an engine that silently lacks it. `WebApiFeatures.Default` is every non-network feature and will never include fetch.

**Timers are the one web API that changed engine infrastructure, and the contract is narrow enough to state in full.** `TimerQueue` (`Jint/WebApi/Timers/TimerQueue.cs`) is a min-heap of due times plus an id map, engine-thread-only and lock-free, reached from `Engine._webApi` (`Jint/Engine.WebApi.cs`) — null on any engine that did not enable the feature, which is what every hot path consults first. Four rules hold it together. **The single job queue is the microtask queue:** `EventLoop.RunAvailableContinuations` promotes exactly *one* due timer, and only when `TryDequeue` has failed, so everything a job queues transitively runs before the next timer is looked at (`Promise.resolve().then` beats `setTimeout(0)`; each timer gets its own checkpoint; an interval cannot starve reactions). Promoting more than one, or promoting before the dequeue, breaks HTML ordering — both mutations are caught by `TimerTests.EachTimerGetsItsOwnMicrotaskCheckpoint`. **Anything else that is a *task* re-queues while `HasPendingEventLoopJobs`, with one pump per feature** — `SchedulerQueue`, `PerformanceObserverRegistry`, `FileReadQueue`; a checkpoint written per instance deadlocks once two are live, each deferring on the other's pending job. **There are no background threads:** the clock is `TimeProvider.GetTimestamp`/`GetElapsedTime` and never `TimeProvider.CreateTimer`, so a timer fires on the next pump at or after its due time and an engine nobody pumps never fires one. Since a timer coming due enqueues nothing and therefore wakes nobody, the two wait loops bound themselves by `Engine.TimeUntilNextPumpScheduledWork()` instead — `Engine.DrainEventLoopUntil` clamps its poll interval, and `AwaitPromiseSettlementAsync` takes `EventLoop.WaitForEventAsync(TimeSpan, CancellationToken)`, one `Task.Delay` per idle wait and only while something pends. Both skip the wait entirely when something is due already, *unless* `IsRunningJob` says the queue is unrunnable from here, where an early return would spin hot for the caller's whole timeout. **A restore clears the queue:** `ResetTransientEvaluationState` calls `_webApi?.ResetTransientState()` beside `Modules?.DiscardPendingLoads()`, and each entry additionally carries its registration-time `EventLoopGeneration` into the job it is promoted as, so the generation fence catches one already in flight. **An interval is re-armed before its callback runs**, which is both what the specification says (step 8.2 precedes 8.4) and what stops a throwing callback silently killing it — pinned by `TimerTests.AThrowingCallbackDoesNotStopTheInterval`. Timer callbacks are jobs like promise reactions: same constraint budget, and a throw erupts from whatever is pumping — unless a `DiagnosticsSink` is set, which is what turns that into report-and-continue (see [Diagnostics](#diagnostics-and-reporterror)).

**`Atomics.waitAsync` timeouts ride the same pump, and are the reason `Jint/Engine.Pump.cs` exists.** They are *core* — every target framework, no opt-in — so they cannot live in the net8-only `WebApiEngineState`, and the two hooks the event loop and the wait loops call (`Engine.TryPromoteDueTimerJob`, `Engine.TimeUntilNextPumpScheduledWork`) are declared on every target framework with the conditional compilation inside their bodies, which is what keeps `#if` out of `EventLoop.RunAvailableContinuations`, `DrainEventLoopUntil` and `AwaitPromiseSettlementAsync` entirely. `AtomicsWaiterDeadlines` (`Jint/Native/Atomics/AtomicsWaiterDeadlines.cs`) is a min-heap of `Stopwatch` timestamps hung off `Engine._atomicsWaiterDeadlines`, which is null until the first finite-timeout wait *and again as soon as the last one leaves* — that null is the whole per-job cost. It shares the timers' contract with **one deliberate difference, and the difference is load-bearing: the check runs once per pump iteration, not only when the job queue is exhausted.** test262's `$262.agent.setTimeout` is a promise chain rather than a timer, so a test polling for its own `waitAsync` keeps the queue permanently non-empty and a deadline consulted only at exhaustion would never be consulted at all; `AtomicsWaitAsyncPumpTests.AMicrotaskSpinThatNeverEmptiesTheQueueStillSeesTheTimeout` fails the moment the call is moved into the exhaustion branch. Ordering is untouched by that, because settling only *enqueues* the resolution, behind everything already queued. **The wait's own settle-once flag is the whole race discipline** between the timeout route and an `Atomics.notify` from another agent's thread: the compare-and-swap in `AsyncWaiter.Resolve` decides, the timeout route leaves the waiter list before it claims (so a notify racing it counts the wait as gone rather than waking one about to report timed-out), and the heap reads the flag without synchronization on purpose — a stale `false` costs one extra pass and nothing else. **A restore drops the deadlines and nothing more:** `DiscardAtomicsWaiterDeadlines()` sits beside `_webApi?.ResetTransientState()`, and the waits stay in their blocks' waiter lists exactly as a wait asking for no timeout always has, so what `Atomics.notify` counts does not depend on whether a wait happened to have a timeout; the generation each waiter captured at registration is the fence for a settlement already promoted into a job.

**The events feature ships the whole DOM dispatch algorithm and no tree to run it over, and both halves are deliberate.** `JsEventTarget.DispatchEvent` (`Jint/WebApi/Events/JsEventTarget.cs`) reads one virtual, `IsNode`, and takes the reduction of the specification's dispatch to the single-item path a tree-less target produces — which is the whole algorithm for an `EventTarget` author code created, not an approximation of it. Every target this engine ships is on that lane, and keeping it there is a promise: it builds no event path, so an `AbortSignal`, a `MessagePort` or a global `error` event allocates exactly what it did before the tree seam existed, which `TreeDispatchTests.ATreeLessDispatchBuildsNoPath` pins structurally rather than by timing. Both passes still run, so `capture` decides *which* pass a listener runs in (a capturing listener on a flat target therefore runs before a non-capturing one whatever order they were registered in), `stopPropagation` ends the dispatch after the current pass while `stopImmediatePropagation` also breaks out of it, each pass walks a clone so a listener added mid-dispatch does not run and one removed does not either, and a `once` listener is removed before it is invoked. **Every listener returns to a microtask checkpoint when the dispatch was entered from a task**, which is WebIDL's *call a user object's operation* running HTML's [clean up after running script](https://html.spec.whatwg.org/multipage/webappapis.html#clean-up-after-running-script), and it is what makes an `XMLHttpRequest`'s `load` and `loadend` — two events fired from one job — order the way a browser orders them ([#3668](https://github.com/sebastienros/jint/issues/3668)). `Engine.CleanUpAfterRunningScript` is the whole of it: the checkpoint is skipped when a *script* started the dispatch (`el.click()`, `target.dispatchEvent(e)`), because then the stack is not empty — and what answers that is the execution-context depth against the depth `RunEventLoopJob` recorded, never `_hostEntryDepth`, which a host `Call` raises with no script on the stack at all. It drains the microtasks at the head of the job queue and stops at the first task, because Jint's one queue holds both and every enqueue site states an `EventLoopJobKind`, with no default, so a new source of deferred work decides rather than inherits. Skipping *past* a task would reorder the one queue, so a microtask behind one still waits for the turn's own drain, which is what every dispatch had before. `Jint.Runtime.EventLoop.WakeJob` exists for that scan: an empty `Action` posted merely to end a park would otherwise stop it, and `Jint.Browser`'s mailbox posts one for the length of every request — so a wake is a shared instance the scan looks past rather than a lambda per call site. **A listener that throws erupts unless the host set a `DiagnosticsSink`**: the specification's "report the exception" (inner invoke step 2.10) needs somewhere to report to, and with a sink that is exactly what happens — the dispatch carries on to the next listener. Without one, swallowing the exception would lose it entirely, so it propagates, the same contract a timer callback has, with the dispatch state unwound in a `finally` either way. Both halves are pinned: `EventTargetTests.AListenerThatThrowsEruptsFromDispatchEvent` for the sinkless engine and `DiagnosticsTests.AThrowingListenerIsReportedAndTheDispatchContinues` for the other, and neither may be "fixed" into agreeing with the other. **A host that has a tree gets `EventDispatch` instead** (`Jint/WebApi/Events/EventDispatch.cs`): the capture, target and bubble phases over a real path, retargeting, `composedPath()` with the closed-tree hiding, and activation behaviour — every step written against seams on `JsEventTarget` (`GetParent`, `TreeParent`, the four shadow queries, `HasActivationBehavior` and its three algorithms) whose defaults say "not in a tree". **Every root that algorithm needs comes from one walk**: `GetRoot()` is asked once for the dispatch target and once for the event's related target, and each path item's root is derived from the step that produced it — a step that stayed inside one node tree has not changed root — so a dispatch is linear in the depth of the tree rather than quadratic in it (#3595). `GetRoot()` is a seam as well, and the only one a host overrides for cost rather than for meaning; an override must answer the target the `TreeParent` walk would have ended on, because the dispatcher steps from tree to tree rather than from node to node. **Every one of those walks is bounded at 10 000 targets** — `JsEventTarget.MaxTreeDepth`, and passing it throws an `InvalidOperationException` naming the host type and the seam (`GetParent`, `TreeParent` or `ShadowHost`) that is answering a cycle (#3596). Nothing else could stop it: the walk is the host's answers rather than script, so no execution constraint counts a step, and a `GetParent` naming a target twice grows the path list until the process runs out. The number is far above any tree an event is dispatched over, the check is one increment per step — a revisit set would allocate on every dispatch to catch the broken host that never comes — and it is deliberately not a `TypeError`: a page must not be able to catch the engine's only report of its host's bug. Nothing in that file knows what a node is; it asks the target, which is what lets the same dispatcher serve Jint's own browser package and, offered upstream, AngleSharp.Js. The one seam a host must not forget is `IsNode`, because it is what selects the lane at all — overriding `GetParent` without it dispatches to the target alone, in silence. Two smaller things worth knowing before editing: `AbortSignal`'s abort algorithms (internal `AddAbortAlgorithm`/`RemoveAbortAlgorithm`) run **before** the `abort` event and are what `fetch` will hang its `CancellationToken` on, which is why the engine cancels that token first of all; and `AbortSignal.timeout()` is an entry on the very `TimerQueue` above, so the events feature creates `Engine._webApi` even when the timers flag is off, and a timeout signal fires only while the engine is pumped.

**The console's object rendering is bounded first and Node-compatible second, and the order matters because the two conflict.** `ConsoleFormatter` (`Jint/WebApi/Console/ConsoleFormatter.cs`) serves `%o`, `%O`, `console.dir`, every non-string top-level argument and every `console.table` cell, and the Console Standard says nothing normative about any of them — [Formatter](https://console.spec.whatwg.org/#formatter) hands `%o` to "optimally useful formatting" and `table`'s entire normative text is one sentence followed by "TODO: This will need a good algorithm." So the target is what Node and QuickJS emit, because the only thing *correct* can mean for a diagnostic is that a script author recognizes it: `Promise { <pending> }`, `Map(1) { 'a' => 1 }`, `Uint8Array(3) [ 1, 2, 3 ]`, `[String: 'x']`, `[Function: foo]`, `[Object: null prototype] {}`. **Every one of those readings is an internal-slot read**, and that is the rule to keep rather than the table: `source`, `flags`, `byteLength`, `toISOString` and `name` are all configurable, so reading a value *through the property of that name* is calling whatever a script left there. `Function.GetOwnFunctionNameForDisplay` and `DatePrototype.FormatIsoString` exist for exactly this, and a new exotic gets the same treatment or it does not get rendered. **A proxy renders as its target and is unwrapped before anything else looks at it** — walking one reaches the `ownKeys` and `getOwnPropertyDescriptor` traps, and until #3316 that made `console.log(proxy)` a way to run arbitrary script and to throw out of a log statement; `ConsoleTests.NeverRunsScriptWhileInspecting` is what stops that coming back. **A function is named, never printed**, because `Options.RetainFunctionSourceText` turns `Function.prototype.toString` into a whole function body in one record, and an unbounded record is the one thing the depth and entry caps exist to prevent. Two divergences from Node follow from that same bound and are deliberate: an `ArrayBuffer` carries no `[Uint8Contents]` hex dump, whose length would be the buffer's length, and own extra properties on an exotic are not appended, so a `Map` shows its entries and nothing else. **A third divergence is a scope line rather than a bound**, and it is the one a reader notices first: nothing is labelled by its constructor or its `Symbol.toStringTag`, so `Math` renders `{}` where Node renders `Object [Math] {}`, and a class instance renders `{ x: 1 }` where Node renders `Point { x: 1 }`. Adding it is possible without running script — the prototype's own `constructor` slot read as a *descriptor*, then `Function.GetOwnFunctionNameForDisplay` — but every step of that walk has to refuse an accessor, and the label is worth less than the refusals cost. Pick it up deliberately or not at all; do not reach for `obj.Get("constructor")` on the way.

**There are two renderers now, they share their readers and not their vocabulary, and that split is the thing to preserve.** `ConsoleFormatter` still writes Node's text; `Jint.Diagnostics.ValueInspector` (all target frameworks, not net8-gated, `[Experimental("JINT0002")]`) writes Chrome DevTools' — `Array(3)`, `ƒ f()`, `class C`, `Promise { <fulfilled>: 1 }` — because it exists to become a CDP `Runtime.RemoteObject.preview` and matching Node there would be matching the wrong thing. What they share is `Jint/Diagnostics/ValueSlotReader.cs`: the proxy unwrap, the date/regexp/buffer/boxed-primitive slot reads, the function kind, the accessor label. **Put a new slot read there rather than in either renderer**, or the two will eventually disagree about what an object *is* while only meaning to disagree about how to write it down. One reader is the inspector's alone and deliberately unused by the console: `ConstructorName`, the descriptor-only prototype walk the console decided against above. `ErrorText` is shared, and the reason it is worth reading before touching either renderer is that the obvious implementation is wrong twice over. `ErrorInstance.ToString()` is `Error.prototype.toString`, which is `Get("name")` plus `Get("message")` — both configurable on every error and definable on any subclass, so the console was a way to run script from a log statement and to throw out of one ([#3598](https://github.com/sebastienros/jint/issues/3598)). But a *getter-free* read that simply refuses every accessor is wrong in the other direction: `DOMException`'s `name` and `message` are WebIDL prototype accessors by design, so it answers `Error` for every `AbortError` the engine has. The reader therefore asks the instance first — `IErrorTextSlots` (`Jint/Native/Error/ErrorInstance.cs`), which `JsDomException` implements and which nothing a script can build implements — and only then walks descriptors, falling back to `ConstructorName` and to `Error`. An interface rather than a type test because the reader is not net8-gated and the type is. `ConsoleTests.NeverRunsScriptWhileInspectingAnError` and `ValueInspectorTests` hold both halves.

**The console's structured record is the same emit, not a second one.** Every method funnels through one `ConsoleInstance.Emit`, which builds a `ConsoleRecord` and makes exactly one `ConsoleSink.Write(in ConsoleRecord)` call; the base implementation forwards to the string overload only when `Message` is non-null. So the methods that act without printing — `groupEnd`, `countReset` on an existing counter, `time` on a new label — reach a structured sink and no string sink, which is what lets a CDP consumer track the group stack, and `WebApiConsoleRecordTests.AStringOnlySinkSeesTheSameTrafficItAlwaysDid` is what stops a new record leaking into the old channel. The two calls that produce no record at all are the two the specification abandons at step 1 (a logging method with no arguments, `assert` with a truthy condition); adding a record there would be a divergence, not a completion. `[ArgCount]` on the fixed-arity methods is what makes an omitted argument *absent* from `Arguments` rather than an `undefined` the script never wrote.
#### The document-shaped fetch settings

**Fetch, cookies and the observer have a file of their own.** The five `Options.WebApi.Fetch` settings that turn `fetch` into a browsing position, the per-hop referrer/`Origin`/`Cookie` recomputation, `CookieContainerCookieJar`, and the engine-free `FetchObserver` seam are [`Fetch/AGENTS.md`](Fetch/AGENTS.md). The one rule to carry across: an observer callback never sees a `JsValue` and never runs on the engine thread.

#### Diagnostics and reportError

**`DiagnosticsSink` (`Jint/WebApi/DiagnosticsSink.cs`) is the one channel for the script errors a host cannot catch**, and the only web-API surface no feature flag governs: `Options.WebApi.Diagnostics.Sink` arms it on its own, so an engine that named no feature at all still gets it (`Options.Apply`'s condition, and the early return at the top of `WebApiRegistration.Apply` that gives such an engine the channel and *no* globals — not even `DOMException`). `WebApiFeatures.Reporting` (`1 << 15`) governs only the `reportError` global, whose whole implementation is HTML's *report an exception* reduced to its last step: this engine's global object is not an `EventTarget`, so nothing is fired, *notHandled* stays true, and "the user agent may report exception to a developer console" is the sink. Without a sink `reportError` is a no-op that never throws; its one failure is WebIDL's arity error for a bare `reportError()`.

Three things to hold on to when touching it. **The sink decides erupt-versus-report, so it is snapshotted at engine build time** into `Engine._webApi.Diagnostics` (and into `TimerQueue.Diagnostics`, so `TimerEntry.Fire` costs a field read and an entry costs no extra reference) — deliberately unlike `ConsoleOptions.Sink`, which is read afresh per emit: a contract that flips mid-script would be unreasonable, and reading `Options.WebApi` from `Engine.OnPromiseRejectionTracker` would force the lazy options group on a *default* engine and mutate shared `Options` from an engine thread. **Only a `JavaScriptException` is ever reported.** All five catch sites (`TimerEntry.Fire`, `JsEventTarget.InvokePass`, `TimerFunctions.InvokeMicrotask` for a `queueMicrotask` callback, `IdleCallbackQueue.InvokeCallback` for a `requestIdleCallback` one, and `PerformanceObserverRegistry.Invoke` for a `PerformanceObserver` one, which performs the checkpoint on its way out too, so one delivery of several observers is checkpointed between them — HTML invokes the microtask with the same WebIDL `"report"` exception behaviour a timer handler gets, and the algorithms that reach an idle callback or an observer say `"report"` too) key on that type alone with a `when (… is { } diagnostics)` filter, which is precisely the MustPropagate rule stated positively: `ExecutionCanceledException`, `TimeoutException`, `MemoryLimitExceededException`, `StatementsCountOverflowException`, `RecursionDepthOverflowException` and `OperationCanceledException` are all `JintException` but none is a `JavaScriptException`, so a budget still bounds. With no sink there is no `catch` clause at all, which is what keeps the sinkless engine byte-identical. **The promise half is additive and ordered:** the notification raises `Tasks.PromiseRejectionTracker` first and *then* calls `_webApi?.ReportPromiseRejection`, so the pre-existing public event cannot be perturbed by a sink. And it reports at **HTML's** cadence rather than at `HostPromiseRejectionTracker`'s: `Engine.OnPromiseRejectionTracker` only moves the promise between HTML's two lists, and `Engine.NotifyAboutRejectedPromises` is what reports — run from the microtask checkpoint (the job queue running dry in `EventLoop.RunAvailableContinuations`, and the end of a host entry that completed, which is what covers an `Invoke` or a `Call` that never drains). So `Promise.reject(e).catch(f)` raises nothing at all, which is what a browser does and what `customElements.whenDefined('bad name')` needs; a `RejectionHandled: false` report means nothing in that whole turn handled it. `preventDefault()` on `unhandledrejection` is HTML's *notHandled* and decides whether a later handler completes the pair with a `rejectionhandled` — it still suppresses nothing on the sink, which script may not silence.

**`scheduler.postTask` is deliberately not a sixth site, and the asymmetry is normative rather than an oversight.** Prioritized Task Scheduling (<https://wicg.github.io/scheduling-apis/#schedule-a-posttask-task>) is a WICG draft, not a WHATWG living standard, and it invokes its callback with WebIDL's *other* exception behaviour: "Let callbackResult be the result of invoking callback with « » and `"rethrow"`. If that threw an exception, then reject result with that." The throw therefore belongs in the promise `postTask` handed the caller — which is what `SchedulerTask.Run` already does — and a rejection nobody handles still reaches a sink, as an `UnhandledPromiseRejection` rather than an `UncaughtCallbackError`. Reporting it as a callback error would tell a host about a failure its own `.catch` had already dealt with. `DiagnosticsTests.AThrowingSchedulerTaskRejectsItsPromiseAndIsNeverReportedAsACallbackError` and its public-interface twin are what stop that being “fixed” into symmetry with the five above.
