## Modules

```csharp
var engine = new Engine(options => options.UseModules(@"C:\Scripts"));
var ns = engine.Modules.Import("./my-module.js");

// or programmatically
engine.Modules.Add("lib", builder => builder.ExportType<MyClass>().ExportValue("version", 1));
```

### Asynchronous module loading

`IModuleLoader.LoadModule` has to hand back a parsed `ModuleRecord` there and then, so a host fetching module source over I/O — HTTP, a Vite dev server, an asset pipeline — could only satisfy it by blocking the calling thread, which is not viable on a game loop or a UI thread. The spec has always allowed better: `HostLoadImportedModule` may complete whenever it likes and call `FinishLoadingImportedModule` later. Jint used the spec's names for those hooks but not their shape — there was no load phase at all, and modules were loaded lazily and synchronously from inside `InnerModuleLinking`.

The **load phase** now exists as the spec writes it (`Jint/Runtime/Modules/CyclicModuleRecord.cs`, `ModuleLoadPayload.cs`): `ModuleRecord.LoadRequestedModules` (public, the spec's `LoadRequestedModules`) returns a promise that settles when the transitive graph is present, driven by `InnerModuleLoading` / `GraphLoadingState` / `ContinueModuleLoading`. `ModuleStatus.New` is the state a cyclic module starts in, and every module a single load visited leaves it *together*, when the last pending request settles — not one at a time as each arrives. Three consequences to keep in mind when touching this code:

- **`GetImportedModule` is a lookup now, not a load.** Every module record carries `[[LoadedModules]]`, keyed by specifier and attributes and deliberately *not* by import phase (`import x` and `import defer x` denote one record, so keying on the phase would ask the host twice for one pair). A referrer that is not itself a module — a script, or a host calling `Engine.Modules.Import` — has its list kept by the engine under `(location, request)`, because two scripts at different locations may resolve one specifier differently. That map is what makes the spec's consistency requirement true by construction for every pair that already has an entry: no loader call and not even a `Resolve` call happens for it again. The entry is written by `FinishLoadingImportedModule`, though, so a pair whose *first* call has not finished yet can be asked a second time — which `InnerModuleLoading` does, exactly as the spec writes it, when one module imports one specifier at two phases (`import x` alongside `import defer x`) and the loader is asynchronous. `HostLoadImportedModule` anticipates precisely that and asks for consistency rather than uniqueness — "it must perform FinishLoadingImportedModule … with the same result each time" — and the second request attaches to the in-flight completion, so the outcome is still one module record and one fetch. One extra `Resolve` call is the whole of the difference; do not treat a `Resolve` call as a per-import checkpoint a host can count. `GetImportedModule` keeps a synchronous-load fallback for the paths that predate the load phase (a host calling `Link()` on a module it built itself), and `Link()` runs the load phase itself when it finds a `New` module, so those paths behave exactly as they did.
- **Which errors become rejections is deliberately asymmetric.** For a **synchronous** loader nothing changed: a `JavaScriptException` becomes a throw completion (as it did), and everything else — `ModuleResolutionException`, whatever a host's `LoadModule` threw — still propagates on the caller's thread, because `Modules.Import` has always surfaced those and a `ModuleResolutionException` is not something to flatten into a JS `Error`. For an **asynchronous** loader a failure becomes a rejection instead, because the host reports it through `ModuleLoadCompletion.SetError` or a faulted task, and there is no caller's thread left to throw on. One carve-out cuts across both, and it is not a detail: the failures that exist to *bound* execution never become a rejection on either path. `ModuleLoadCompletion.MustPropagateLoaderException` is the predicate — the engine's own limit and abort exceptions (`ResultLimitExceededException`, `MemoryLimitExceededException`, `StatementsCountOverflowException`, `RecursionDepthOverflowException`, `ParsingLimitException`, `ModuleGraphLimitException`, `ExecutionCanceledException`), an engine-abort `TimeoutException`, an `OperationCanceledException` for the engine's own token, and the CLR failures nothing can recover from (`OutOfMemoryException`, `PlatformNotSupportedException`, `RegexMatchTimeoutException`) — and `ModuleLoadCompletion.Propagate` rethrows them on whatever stack the settle ran on. Do not "unify" these by catching more broadly on the synchronous path: `JintException` is also the base of `ExecutionCanceledException`, `TimeoutException` and the memory/statement-budget exceptions, and a constraint that becomes a promise rejection is a constraint that no longer bounds anything.
- **A load in flight is cross-cycle state.** `ModuleLoadCompletion` captures the event loop's generation at *registration* and enqueues with it, so a settle that arrives after `RestoreGlobalSnapshot` is discarded rather than applied to the restored engine — the same fence every other cross-thread completion sits behind, and the reason the completion never touches the engine on the host's thread. `ResetTransientEvaluationState` additionally drops the in-flight entries (`ModuleOperations.DiscardPendingLoads`), because the map that coalesces concurrent loads of one resolved specifier would otherwise let the next cycle attach to a load whose completion can never land. Modules already loaded stay registered; the module registry is deliberately not part of what a restore reverts. A `ModuleImportOperation` from the ended cycle reports itself completed-and-faulted rather than staying pollable forever, derived from the engine's generation on read rather than pushed at restore time — the contract `StartImport` documents is that the host polls `IsCompleted`, so every way the import can end has to reach that flag. Its `Promise` stays pending: settling it is exactly what the fence forbids.

The three host entry points are not interchangeable, and the difference is which thread runs the engine's turns. `Modules.Import` stays synchronous and blocks the calling thread on the drain — which **deadlocks** if the loader's own completions need that same thread, the Unity-main-thread case. `Modules.ImportAsync` awaits without holding a thread, but its continuations run on whichever thread resumes the await. `Modules.StartImport` returns a `ModuleImportOperation` and runs nothing on its own: the host calls `engine.Tasks.ProcessTasks()` from its own loop and watches `IsCompleted`, which is the only one of the three where every turn provably runs where the host wants it. Note that a host cannot inspect the returned promise itself — `JsPromise` and `PromiseState` are internal — which is exactly why `StartImport` hands back an operation rather than the promise itself.

One settle is exempt from the queue entirely: a completion settled **before `LoadModuleAsync` has returned** runs its continuation on that very stack — the engine initiated the call and is waiting for exactly this answer, so it is at a known-safe point, the same one a synchronous loader's return lands on. The window is per-completion and thread-checked (`ModuleLoadCompletion.Settle`); a settle from any other thread, or from the same thread once the call has returned, is queued as ever, because "the engine thread" is not an identity the engine tracks. The payoff is that an `AsyncModuleLoader` whose `LoadModuleContentsAsync` answers with an already-completed task — a warm cache — makes the blocking `Import` fully synchronous, event loop untouched, exactly as a synchronous `IModuleLoader` would have. For the loads that do stay asynchronous, the blocking drain no longer pays a poll-slice per hop either: every `EventLoop.Enqueue` signals a work-arrived event the drain waits on (`EventLoop.WaitForWork`), with the old 10ms cadence kept only as the backstop — and the wait deliberately ignores a non-empty queue while nested inside a job (`IsRunningJob`), where the re-entrancy guard makes those jobs unrunnable and an early return would spin hot for the caller's whole timeout.

A blocking import nested inside a job does not reach that wait at all, though. `ModuleOperations.ThrowIfBlockedInsideJob` fails it up front with an `InvalidOperationException` naming `StartImport`/`ImportAsync`, because the wait it would enter cannot end in anything but the `PromiseTimeout`: the queued completion that would settle the load is exactly what the re-entrancy guard makes unrunnable from there. Ten seconds of stall and "the loader did not finish in time" is the wrong answer to a structurally impossible wait — the guard above is what keeps that wait cheap for the cases that *can* progress, not a licence to enter it when none can.

**Which of the two a given load takes is not something a host can predict**, and nothing reports it afterwards. It is decided by whether the loader's answer happens to be at hand before `LoadModuleAsync` returns, so one loader settles inline on a cache hit and queues on a miss, and a task that completes on the thread pool can land on either side of that return depending on nothing but how busy the machine is. For an ordinary failure the difference is invisible — it is the same rejection either way. For one of the propagating failures above it decides *where* the exception erupts: inline, out of the very call that started the import (`Modules.Import`, `ImportAsync`, `StartImport`); queued, out of whatever pumps the event loop afterwards, with the importing promise left unsettled and its `ModuleImportOperation` never completing — so on that side the erupting exception is the whole outcome, and a host that only polled `IsCompleted` would poll forever. Both are behaviour rather than an accident, which is why a test asserting either has to *select* its window instead of letting the machine pick one: `AsyncModuleLoaderTests` pins one test on each side (`AResultLimitSettledInsideTheLoadCallStaysFatalOnTheImportingStack`, `AResultLimitSettledAfterTheLoadCallReturnedStaysFatalOnThePumpInstead`), and a change that ever makes the two agree updates both rather than deleting one.

### Gotchas

Each of these cost a real integrator or a real bug. These are the ones that bite in this area; the
rest of the list is split across the files indexed from the repository-root [`AGENTS.md`](../../../AGENTS.md).

- **A module's location is the name its loader chose, and four things read it.** `ModuleFactory.LocationOf` is the whole rule: `resolved.Uri.LocalPath` for an absolute `file:` uri, `resolved.Key` — the loader's own string, verbatim — for everything else, including a relative uri and no uri at all. It is deliberately not `Uri.AbsoluteUri`, which strips a default port, lowercases the host, collapses dot segments and percent-encodes, and whose .NET Framework and .NET Core parsers disagree on some of that, so the same host code would get a different name per target framework. What consumes the string: it is `ModuleRecord.Location`, the `referencingModuleLocation` echoed back into `ModuleLoader.Resolve` for that module's own imports, `SourceLocation.SourceFile` (so it reaches `error.stack` and is the debugger's `BreakLocation.Source`), and the only name a host has to report through `import.meta.url` — Jint leaves `import.meta` itself to `Host.GetImportMetaProperties`, whose default is empty. Two consequences. A host that names a module *before* one exists — anything sharing a `Prepared<Module>` — Acornima's AST node — across pooled engines, which passes the name as `Engine.PrepareModule`'s `source` argument — has to reproduce the engine's answer exactly or relative imports resolve against the wrong base with nothing to point at, which is why `LocationOf` is public rather than a private helper. And the location is never null now: the JSON, bytes and text factories used to be `resolved.Uri?.LocalPath` with no fallback, so a loader returning no uri handed back `ModuleRecord.Location == null` against a property declared `string`. Pinned from the embedder's side in `Jint.Tests.PublicInterface/HostModuleLocationTests.cs`.
