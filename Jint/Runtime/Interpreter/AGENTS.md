# Agent instructions: the interpreter

>
> This is one of the co-located instruction files indexed from the repository-root
> [`AGENTS.md`](../../../AGENTS.md). Read that first — it carries the build and test commands, the branch to
> target, and the conventions that apply to every file in the repository. Nothing below is

### Engine-affine vs shareable state

- **`Prepared<Script>` / `Prepared<Module>` are reusable and thread-safe** and may be shared across engines. The guarantee is documented on `Engine.PrepareScript` / `Engine.PrepareModule` (not on `Prepared<T>` itself); `Jint.Tests.CommonScripts/ConcurrencyTest.cs` runs one prepared AST on several engines in parallel.
- **Why that holds:** interpreter handler trees accumulate per-node inline caches that are engine-affine, so they are engine-owned (`Engine._functionDefinitions`, `Engine._scriptStatementLists`) and never shared through the AST. The rule for AST `UserData` is *nothing engine-affine may be stashed there* — not *nothing mutable*: mutable but engine-independent state (slot arrays, a compiled-RegExp memo) is deliberately allowed. Where such state depends on something an engine configures, the way an adapted regex depends on `Options.Constraints.RegexTimeout`, the publication carries the *value* it was built for and is rebuilt on a mismatch (`JintLiteralExpression.AdaptedRegExp`, sebastienros/jint#3442) — never an engine reference and never an engine-keyed table, and the rebuild has to be cheap enough that two engines alternating on one node is a non-event. `JintStatement.Build` carries an explicit `INVARIANT` comment saying so (`Jint/Runtime/Interpreter/Statements/JintStatement.cs:66`); `JintExpression.Build` relies on the same rule but has no equivalent comment. `Jint.Tests/Runtime/GarbageCollectionTests.cs:135` → `SharedPreparedScriptDoesNotRetainEngines` pins it: 20 engines run one prepared script and every one must be collectable while the script stays rooted.
- **`StaticAnalysis = false` moves that publication from prepare time to run time; it does not move it off the AST.** A parse-only preparation (`ScriptPreparationOptions.StaticAnalysis` / `ModulePreparationOptions.StaticAnalysis`) returns a tree with empty `UserData` everywhere, and the state the analyzer would have published is instead published by whichever engine reaches a node first — function definition state (`JintFunctionDefinition.Initialize`), block state (`JintBlockStatement`'s `UserData ??=`) and literal values (`JintLiteralExpression.Build`). Those are the three lazy publications that already existed for source-mode programs; nothing new writes to `UserData`. So the invariant above is what makes the option safe, and it now has to hold node for node at run time rather than merely by construction at prepare time: everything published is engine-neutral, several engines may publish the same node concurrently, and last-writer-wins is the intended outcome. The rest of what the analyzer produces (identifier binding names, the determined member-access value, a script root's hoisting scope, folded unary/binary constants) is rebuilt per engine and never published. Pinned by `Jint.Tests/Runtime/ParseOnlyPreparationRaceTests.cs` (16 engines racing a first evaluation, then a convergence assertion) and `SharedParseOnlyPreparedScriptDoesNotRetainEngines` / `SharedParseOnlyPreparedModuleDoesNotRetainEngines` in `GarbageCollectionTests.cs`.
- **`Prepared<T>.ReferencedGlobals` inherits that contract** — it is built once at prepare time and fully immutable afterwards (sorted `string[]` plus an eagerly built lookup, no lazy init that would need synchronization under concurrent readers), so it is safe to read from every engine sharing the `Prepared<T>`. It is `null` unless `CollectReferencedGlobals` was set, which is deliberately distinguishable from an empty set. The collector never touches AST `UserData` and holds nothing engine-affine.
- **`Options` is meant to be shared** across engines, including concurrent ones. Constraints carry per-execution state (a statement counter, a deadline), which used to break that; the built-in helpers now register a **factory** so each engine gets its own instance. The instance overload `Constraint(Options, Constraint)` stays documented as single-engine-only — nothing can be cloned out of an arbitrary user-derived `Constraint`.
- **Shared interop caches may hold only engine-independent values.** Resolved CLR member accessors are cached on `TypeResolver` and shared by every engine using that resolver — and engines constructed without an explicit one all share `TypeResolver.Default`, which lives for the process. The key is `(Type, member name, MemberResolutionRequirement, InteropResolutionProfile)`; the profile is part of it because two engines whose interop configuration differs must not answer from one another's entries. `TypeResolver.IsShareable` is the exclusion: a `NestedTypeAccessor` never enters the cache (it holds a `TypeReference`, a `JsValue` owned by the engine that created it), and **no member of a type carrying a non-`int` indexer does** when the engine's `ClrTypeConverter` claims that indexer's index type — `TypeResolver.IsConverterNeutral`, which is asked on the way out of the cache as well, since an entry a stock engine stored must not be served to one whose converter would have resolved it differently, nor the reverse. It is asked of the *type* rather than of the resolved accessor because the converter's one answer — does the member name convert to an index key — also decides whether a plain `PropertyAccessor` carries an indexer probe, and that is invisible in the artefact (sebastienros/jint#3436). The converter is deliberately not in the profile: that would have cost every engine with one the whole shared cache for the sake of that single question. `TypeReference`'s static members go through the same resolver rather than a cache of their own: `GetStaticAccessor` keys `(Type, member name, InteropResolutionProfile)` — no requirement, because the static lane never filters by one — and applies the nested-type exclusion only, that lane never probing an indexer and so never consulting the converter. Its one deliberate opt-out is an **enum** reference, which resolves per instance because the engine's `EnumConversion` mode decides whether a constant is a `JsString` or a `JsNumber` and that key cannot express it. Pinned by `Jint.Tests/Runtime/GarbageCollectionTests.cs` → `NestedTypeAccessDoesNotRetainEngines`. A resolver's cache keeps the reflected `Type`s alive for as long as the resolver does, so give a private resolver to any engine that must not outlive the types it touches.
- **A shared cache's key must carry everything its value was built for**, and the other family of them is in `DefaultTypeConverter`: the CLR delegate a JavaScript function converts to is memoized per function *instance*, and the compiled binder below it per *AST node* — process-wide state that a shared `Prepared<Script>` keeps alive past every engine that ran it. Neither key carried the target delegate `Type`, which is the one thing `BuildTargetBinderDelegate` bakes in, so a function converted for a second delegate type was served the first one's delegate and two engines with different host types running one preparation disagreed according to which evaluated first — the loser getting `ArgumentException: Object of type 'Notify' cannot be converted to type 'Transform'` (sebastienros/jint#3434). Both are keyed by target type now, which is also what the memo exists for: one `Delegate` per *(function instance, delegate type)* is exactly the identity an event `-=` needs, where one per function instance was only accidentally it. What that adds to the AST node stays engine-neutral — a `Type` and a binder that takes its target as a parameter, never an engine — and `GarbageCollectionTests.SharedPreparedScriptConvertingFunctionsToDelegatesDoesNotRetainEngines` is the pin.
- **The operator-overload table is the same rule in the interpreter, and what it holds is the candidate set rather than the answer.** `JintBinaryExpression._operatorCandidates` remembers which operator *methods* a `(name, left type, right type)` triple offers — a reflection scan of the two types and nothing else, so no engine, no configuration and no argument value takes part in building one. **Which of them applies is not cached at all**, because three things decide it and none of them is in that triple: `Options.Interop.ValueCoercion`, which `InteropHelper.CalculateMethodParameterScore`'s gray-zone rule consults; the installed `ClrTypeConverter`, whose answer *is* the last rule — a conversion it confirms keeps the candidate, one it refuses scores −1 and discards it; and the **argument values**, since a number scores a perfect fit for a `byte` parameter inside that range and no match at all outside it. Caching the selected `MethodDescriptor` let whichever engine evaluated first decide for every engine after it (sebastienros/jint#3424) and then, once that was keyed per engine, let whichever *value* arrived first decide for every value after it — an `OverflowException` out of `Execute` in one order and the wrong overload, silently, in the other (sebastienros/jint#3567). Selection therefore runs on every evaluation, which is affordable because the scan is the expensive half and scoring one or two candidates is not: a pair with no operator leaves through the empty set without allocating the argument array, a candidate appearing on both operand types is listed once, and `FindBestMatch` builds no list until a *second* candidate survives scoring. Two consequences for anyone adding to this. A cache in this area may hold only what the reflection scan answers — anything a score reads belongs to the evaluation, not to the table — and a new scoring rule reading a value inherits that constraint rather than needing a new key. `JintUnaryExpression._knownOperators` still caches a resolved method on purpose: it takes the first one-parameter method of that name and computes no score, so it asks none of the three; anything that gives it a scoring step inherits these rules with it.

### Gotchas

Each of these cost a real integrator or a real bug. These are the ones that bite in this area; the
rest of the list is split across the files indexed from the repository-root [`AGENTS.md`](../../../AGENTS.md).

- **Coverage counters live engine-side, keyed on AST node identity, and that is not an implementation whim.** `Engine._coverage` (`Jint/Runtime/Coverage/`) is null on every engine that did not opt in, and the *only* caller of the method it is read from is the per-statement lane above — so the off path is an uncalled method rather than a folded branch. A hit-count field on `JintStatement` would look cheaper and be wrong: `ConstantStatement`, the handler for `return <literal>;`, is parked on the AST node's `UserData` by the static analysis pass (`Engine.Ast.cs`) and is therefore ONE instance shared by every engine running a prepared script, so such a field would pool the counts of every engine running that statement. Two consequences for anyone touching the interpreter. A new statement fast path that skips `EvaluationContext.RunBeforeExecuteStatementChecks` must be gated on `ShouldRunPerStatementChecks` exactly as the existing ones are, or it silently stops being counted; and a fast path that produces a statement's result *without executing it* must additionally consult `EvaluationContext.BypassStatementFastPaths` (the frozen `debug mode or coverage` snapshot), which is what the pre-resolved literal return in `JintStatementList.Execute` does.
- **The handler-tree caches engage only on the *second* evaluation of a given script on a given engine.** A host that builds a fresh engine per operation never reaches them, by design. This concerns that cross-run carry-over only — caches which are not engine-scoped still pay back, and CLR member resolution in particular now survives across engines through the shared `TypeResolver` described above, which is the main reason a fresh engine per operation costs less than it used to. `Engine.Advanced.RestoreGlobalSnapshot` deliberately **preserves** these caches (`_scriptStatementLists`, `_functionDefinitions`, `_evaluatedScripts`) while resetting the globals — reaching them from a host that used to need a fresh engine per evaluation is the entire point of that API, and `Jint.Tests/Runtime/GlobalSnapshotInternalsTests.cs` pins it.
- **A warmed member-read site retains its last receiver.** The prototype-method inline cache stores the receiver, its direct prototype and the resolved descriptor on the handler node (`JintMemberExpression._cachedProtoReceiver`), and only replaces that entry when the same site later caches a *different* receiver — a miss that does not qualify for caching leaves the old one in place. Handler trees are engine-owned and survive between evaluations on a re-running engine, so a pooled engine can hold one host object alive per warmed call site until its next run. Nothing clears these: `Engine.Advanced.ResetCallStack` releases call frames only. A host whose receivers wrap large native state that must not outlive a run should drop the engine rather than pool it. **A warmed *call* site retains its last callee the same way, and one of the two caches is heavier than it looks.** `JintCallExpression._fastCallee` (the built-in fast-call lane) usually holds a realm intrinsic, which the realm roots anyway — but the field is written for whatever `Function` an eligible site dispatched, before and regardless of the shape verdict, so a site with at most two arguments and no spread calling an *interpreted* function pins that too. `_regCallee` (the register-argument lane for interpreted callees) holds a `ScriptFunction` by construction, and a `ScriptFunction` holds the environment it closed over — so a warmed site pins one closure instance, and transitively whatever that closure captured, for the engine's lifetime. It is the same bounded, one-entry-per-site hazard, with the same remedy: drop the engine rather than pool it when the retained graph matters. The bound is per site, not per callee: a polymorphic site overwrites its entry rather than accumulating. The sibling `_regProbedCallee` records what the probe last examined so a rejected callee is not re-probed on every dispatch, and it retains that reference too — for an accepted callee it is the same object as `_regCallee`, so the ceiling stays one live callee per site either way. **Which sites are in the retaining set is decided at build time**, by `_fastArgsEligible` and `_regLaneEligible`: a site with five arguments, or with a spread, can arm neither lane and so records nothing at all. Note also that a site only enters the set once its handler tree outlives the evaluation, i.e. from the second run of the same program on the same engine — a host re-parsing its source every time never warms one, and a `WeakReference` test written against `Execute(string)` therefore proves nothing.
- **A numeric literal's value comes from `AstExtensions.NearestDouble()`, never from `NumericLiteral.Value`.** The scanner accumulates a literal's digits into a `ulong` where it can and hands everything else to `double.Parse`, and both roundings are wrong somewhere Jint ships. No runtime before .NET 9 rounds `ulong` → `double` once: in `[2^63, 2^64)` it rounds twice and lands one ULP off for about one operand in six, so `(12345678901234567890).toString()` read `12345678901234570000` on `net472` and `net8.0` and `12345678901234567000` on `net10.0` — two different numbers, not two printings of one (sebastienros/jint#3530). And .NET Framework's `double.Parse` is not IEEE correctly-rounded, so the other branch — a fraction, an exponent, more digits than the accumulator holds — moved on `net472` for its own reason (sebastienros/jint#3533); there is no digit count below which that one is safe, since a subnormal literal like `3.3e-311` is wrong about half the time at any width, which is why the trigger is the literal's *shape* and never its length. `NearestDouble` re-reads the literal's own text for both: the octave through `NumberParser.UInt64ToDouble` in whichever radix the scanner used, and every decimal literal carrying a fraction, an exponent or more digits than a `ulong` holds through `NumberParser.TryParseDouble`. A radix literal wider than a `ulong` is re-read through `NumberParser.TryParseRadixInteger`, because the scanner rebuilds that one by accumulating into a `double` a digit at a time and so rounds once per digit — wrong on every target framework, this one owing nothing to the platform (sebastienros/jint#3536) — and a wide *legacy octal* literal moved further than a ULP, since the scanner abandons its accumulator and re-reads those digits as decimal, which is the wrong base. Everything the scanner already rounded once is handed back exactly as scanned. All three readers go through it — `JintLiteralExpression.ConvertToJsValue`, the literal-operand build in `JintAssignmentExpression`, and `AstExtensions.LiteralKeyToString` — and a fourth reader of `.Value` reintroduces the divergence on the target frameworks most embedders ship. It is a workaround for adams85/acornima#53 and comes out when a release carrying the fix is picked up; `Jint.Tests/Runtime/NumericLiteralPrecisionTests.cs` pins the value on every target framework, with an exact `BigInteger` oracle over the affected shapes.
- **A suspension point that publishes no node makes every enclosing statement re-run its test on resume.** Jint resumes a generator or async function by replaying its body, and `JintWhileStatement`, `JintForStatement`, `JintDoWhileStatement`, `JintIfStatement`, `JintSwitchStatement` and `JintTryStatement` each ask `JintStatement.GetSuspensionNode` whether the suspension point lies inside them. That answer is the only thing stopping them re-evaluating the test which already chose the branch execution is standing in — and by then the suspended code has usually moved the state that test reads, so re-running it sends the resume down the *other* branch and silently abandons the rest of the iteration. `GetSuspensionNode` reads exactly one property, `ISuspendable.LastSuspensionNode`, so a suspension that parks its node in a field of its own and does not surface it there is invisible to all six. `yield*` did exactly that: a delegation's node lives in `_delegatingYieldNode` and an ordinary yield's in `_lastYieldNode` — they cannot share a slot, because `JintYieldExpression` picks its delegation branch on the first and its plain-yield branch on the second — and until sebastienros/jint#3509 only the second was published. A `while` whose test the delegated operand had already falsified ended mid-iteration, and the async half, where a delegation that *completes* also resumes through a replay because the inner step settles on a later microtask, lost one `yield` per level of recursion. Pinned in `Jint.Tests/Runtime/GeneratorTests.cs`, sync and async side by side.
