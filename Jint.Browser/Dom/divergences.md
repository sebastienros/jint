# AngleSharp divergences found by the DOM bindings

**Data, not instructions.** This is the register [`AGENTS.md`](AGENTS.md) points at: every place AngleSharp
answers differently from the standard that the bindings had to work around, so the next agent recognises one
it has already met and nobody patches around the same thing twice. The rule that governs it — record the
divergence, never work around it silently, never open an issue on AngleSharp without being asked — is in that
file, which is where an agent is told to look before it edits anything here.

Divergences that are **AngleSharp's**, found by this work and to be reported upstream rather than patched
here:

| What | The standard | AngleSharp |
| --- | --- | --- |
| `Range.comparePoint` / `isPointInRange` | DOM §5.5 checks the argument root, uses node length (including CharacterData), and includes both endpoints | `IRange.CompareTo` checks its own start root instead of the argument root and validates against child count. `Contains` also uses child count, excludes endpoints, and compares node length instead of the point offset. `DomRangeMembers` performs the standard checks and delegates tree ordering through `CompareBoundaryTo` on a private collapsed clone; same-container queries need no clone. Tracked in [#3915](https://github.com/sebastienros/jint/issues/3915) |
| `node.isConnected` | DOM §4.4: whether the node's shadow-including root is a document | `INode` has no member for it at all, so nothing is projected — and every client library asks a node handle this before it clicks it, so an absent member makes every element read as detached. Re-declared in `additions` |
| `el.dataset.fooBar` and `delete el.dataset.foo` | HTML §3.2.6 converts between property names and `data-*` attribute names, and the deleter removes the content attribute | `IStringMap` accepts raw attribute suffixes and rejects uppercase ASCII. Its deletion bug is fixed in 1.7.3 ([upstream change](https://github.com/AngleSharp/AngleSharp/pull/1310)), but that does not supply WebIDL's name conversion or setter validation: `DomStringMapAdapter` still projects the associated element |
| `el.querySelectorAll(…)` | DOM §4.2.6 returns a static `NodeList` | fixed in 1.8.0: the result implements `INodeList` and `[DomReturnType(typeof(INodeList))]` identifies its IDL projection despite the unchanged CLR signature ([upstream change](https://github.com/AngleSharp/AngleSharp/pull/1318)). The generator consumes that metadata, so `DomStaticNodeList` was removed. `INodeList` already had its indexed getter in 1.7.2; the 1.7.3 indexed-getter addition was to `ITextTrackCueList` |
| `NodeList.item(index)` outside the supported indices | DOM §4.2.10.1 returns `null` | the underlying node-list and query-collection indexers still throw `ArgumentOutOfRangeException` in 1.8.0. **No longer reachable through `NodeList.item`**: DOM §4.2.10's indexed getter is `Collections/DomNodeListMembers.Item`, a `skip` plus an `additions` entry that bounds-checks before it indexes, the way `DOMTokenList.item` already did. Every other `item` operation over an AngleSharp indexer -- `CSSRuleList`, `MediaList`, `NamedNodeMap`, `StyleSheetList`, `FileList`, `TouchList`, `DOMStringList` -- still translates the raise to a `TypeError`; no vendored document reaches one, which is why the fix is one member and not a table
| `el.style.color` | CSSOM serializes an opaque colour as `rgb(r, g, b)` | Css 1.1.0 adds `CssColorValue.UseSpecSerialization`, but the default still serializes opaque colours as `rgba(r, g, b, 1)`. Jint does not change this process-global mutable switch on behalf of every AngleSharp consumer |
| `el.children === el.children` | one `HTMLCollection` per element | a fresh collection per call, so the wrapper cache has nothing to key identity on. The 1.8.0 `[DomSameObject]` annotation documents the promise but does not implement it |
| `document.getElementsByClassName('x')` after the tree or class attributes change | a live `HTMLCollection` of descendants matching the class names | a snapshot. The Document and Element hooks answer a `DomLiveHtmlCollection` that re-runs the collection algorithm on each read ([#3897](https://github.com/sebastienros/jint/issues/3897)); the algorithm it re-runs is this package's own, for the reason the next row gives, so AngleSharp's class matching is not on the path |
| `getElementsByClassName('A a')` in quirks mode | [DOM's class-name collection algorithm](https://dom.spec.whatwg.org/#concept-getelementsbyclassname) compares ASCII case-insensitively in quirks mode and identically otherwise; U+212A KELVIN SIGN stays distinct from ASCII K/k | 1.8.0 compares case-sensitively in both modes. With `<html class="a A"><body class="a a">` and no doctype, the document query returns only `html`, omitting `body`. Current upstream [class matching](https://github.com/AngleSharp/AngleSharp/blob/1b8579bea408b816891c61d047eb80152fc4f9af/src/AngleSharp/Dom/QueryExtensions.cs#L371-L385) still uses `ClassList.Contains`; the CSS class-selector path has the same defect and no comparer overload is exposed. Upstream [AngleSharp#1319](https://github.com/AngleSharp/AngleSharp/issues/1319) and [AngleSharp#1321](https://github.com/AngleSharp/AngleSharp/pull/1321) were declined as out of scope, so [#3899](https://github.com/sebastienros/jint/issues/3899) moved the ownership here: the whole algorithm is `DomHostHooks.GetElementsByClassName` now -- the ordered set of classes, the empty-set answer, and an ASCII-only fold read from the node document's `compatMode` on every read of the live collection. AngleSharp's own query is no longer on the path
| `:lang(en)` on an element with no declared or inherited language | [Selectors §8.1](https://drafts.csswg.org/selectors-4/#the-lang-pseudo) matches the element's content language; an element whose language is unknown matches no language range | 1.8.0 falls back to `IBrowsingContext.GetCulture()`, so the element matches on an English-culture context and does not on an invariant one. `ParserDriver` supplies the page engine's `Options.Culture` to make that fallback independent of the parser thread, and the browser WPT lane pins invariant culture, but neither changes AngleSharp's matching rule. An upstream report has been drafted but not filed |
| `:enabled` and `:disabled` on a link, on `<fieldset disabled>` or `<optgroup disabled>`, and inside a disabled `select` or an outer disabled `fieldset` | [HTML §4.16.3](https://html.spec.whatwg.org/multipage/semantics-other.html#selector-enabled) matches `:enabled` against the seven element types which have a disabled state and `:disabled` against every [actually disabled](https://html.spec.whatwg.org/multipage/semantics-other.html#concept-element-disabled) element. `disabled` is a boolean attribute, an `optgroup` or `option` is disabled by its nearest ancestor `select`, a `fieldset` inside a disabled fieldset is a disabled fieldset itself, and a disabled fieldset excuses only its own first `legend` | Css 1.1.0's `IsEnabled`/`IsDisabled` give a link a disabled state; read the *value* of `disabled` on an `optgroup`, `menuitem` or `fieldset`, so `<fieldset disabled>` matches `:enabled` and never `:disabled`; stop at the nearest ancestor fieldset even when that one shelters the element in a legend and an outer one does not; and know nothing of the `select` above an `optgroup` or `option`. `PagePseudoClassSelectorFactory` owns §4.15's disabled state outright, over element interfaces and attribute presence, and asks AngleSharp only for the two selectors' text and specificity. AngleSharp 1.8.1 fixes the link half ([AngleSharp#1324](https://github.com/AngleSharp/AngleSharp/issues/1324)); the boolean-attribute and ancestor-state differences still require this override |
| `:target` with duplicate IDs, a matching shadow-tree ID, or a disconnected element | [Selectors §8.2](https://drafts.csswg.org/selectors-4/#the-target-pseudo) matches the document's target element; HTML selects the first matching ID or legacy named anchor in the document tree, trying the raw fragment before its percent-decoded form | 1.8.0's `IsTarget` compares each candidate's ID with its owner document's location, so every duplicate, a shadow descendant, and a disconnected clone can match. `PagePseudoClassSelectorFactory` selects the one indicated element from the HTML document instead. No upstream issue has been filed |
| `:any-link` / `:link` / `:visited` on HTML and SVG hyperlinks | [Selectors §8.1](https://drafts.csswg.org/selectors-4/#the-any-link-pseudo) makes `:any-link` exactly the union of the two link-history states; HTML makes every `a[href]` and `area[href]` a hyperlink even when the attribute is empty, while SVG makes an SVG `a` with either `href` or `xlink:href` a hyperlink unless it descends from another hyperlink element | AngleSharp 1.8.1 fixes HTML hyperlink matching ([AngleSharp#1337](https://github.com/AngleSharp/AngleSharp/issues/1337), [AngleSharp#1338](https://github.com/AngleSharp/AngleSharp/pull/1338)), so `PagePseudoClassSelectorFactory` delegates the HTML partition to the native selectors. The SVG partition still applies the ancestor rule directly over the DOM parent chain, and `:any-link` remains the union of the two states. This browser keeps all hyperlinks unvisited |
| `:default` | [HTML §4.16.3](https://html.spec.whatwg.org/multipage/semantics-other.html#selector-default) matches a submit button which is [its form owner's default button](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#default-button) — the first submit button in tree order the form owns — an `input` the `checked` attribute applies to and which carries it, and an `option` carrying `selected` | Css 1.1.0 matches *every* `button` with a form owner whatever its type, and every `submit`/`image` input with one, so each further button in a form is a default button too; it matches no checkbox or radio at all; and it reads the *value* of `selected`, so `<option selected>` is not one. `PagePseudoClassSelectorFactory` answers the three categories from the markup, deciding the default button over form ownership in tree order. No upstream issue has been filed |
| `:open` and `:closed` | [HTML §4.16.3](https://html.spec.whatwg.org/multipage/semantics-other.html#selector-open) matches `:open` against a `details` or a `dialog` carrying `open`, a drop-down `select` whose drop-down box is open and an `input` whose picker is open; [Selectors §10.5](https://drafts.csswg.org/selectors-4/#open-state) makes `:closed` those same four categories in the other state, which is why neither is the complement of the other over every element | 1.8.0's `IsOpen` is a `return false` with a to-do beside it, so `<details open>` matches nothing, and `:closed` is not in `DefaultPseudoClassSelectorFactory`'s table at all, so a page that spelled it got a `SyntaxError` from every selector API. `PagePseudoClassSelectorFactory` owns both: the boolean `open` attribute decides a `details` and a `dialog`, while a drop-down `select` (§4.10.7's display size, which AngleSharp's `Size` cannot answer because it reports 0 for an absent attribute) and a File Upload `input` (§4.10.5, the one picker the standard requires) have both states and are always closed, since this browser presents no user interface that could open one. No upstream issue has been filed |
| `:in-range` and `:out-of-range` | [HTML §4.16.3](https://html.spec.whatwg.org/multipage/semantics-other.html#selector-in-range) matches both only against an element which is a candidate for constraint validation **and** has range limitations, and §4.10.5.4 makes the `min` and `max` attributes apply to seven type states, gives the Range state a default minimum of 0 and maximum of 100, and clamps a range control's value to them | 1.8.0's `IsInRange`/`IsOutOfRange` ask neither question: any `IValidation` element that is neither overflowing nor underflowing is `:in-range`, so `<input type=text min=0 max=10>` matched, and so did a disabled or read-only control the standard bars. It also reads a range control's value back unclamped, so `<input type=range min=2 max=7 value=1>` reported an underflow. `RangeStateSelector` asks `WillValidate` for the candidacy — AngleSharp's own answer, and a good one — then applicability, then clamps the Range state. Range limitations are read from the presence of `min`/`max` rather than from parsing them, because answering "does this `min` parse" would be a second implementation of HTML's six value formats beside AngleSharp's input-type table. No upstream issue has been filed |
| `:valid` and `:invalid` | [HTML §4.16.3](https://html.spec.whatwg.org/multipage/semantics-other.html#selector-valid) matches an element which is a candidate for constraint validation and satisfies its constraints, a `form` owning no failing candidate, and a `fieldset` with no failing candidate among its descendants; an element [barred](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#barred-from-constraint-validation) matches neither | 1.8.0's pair is `CheckValidity()` and its negation, and `CheckValidity()` is `WillValidate && Validity.IsValid` — so a disabled control, a read-only one, a hidden input and a reset button all answered `false` and came back `:invalid`. A `fieldset` is barred and carries no constraints of its own, so every one of them was `:valid` whatever it contained. `ValidityStateSelector` separates the two halves of that `false` and answers a `fieldset` from its descendants, keeping AngleSharp's answer for a `form`. No upstream issue has been filed |
| `:read-only` and `:read-write` | [HTML §4.16.3](https://html.spec.whatwg.org/multipage/semantics-other.html#selector-read-write) makes an `input` user-alterable only when the `readonly` attribute *applies* to its type state and it is mutable, a `textarea` when it has no `readonly` attribute and is not disabled, and any other element when it is an editing host or editable; `:read-only` then matches **all other HTML elements** | 1.8.0's `IsEditable` asks an input only `!IsDisabled && !IsReadOnly`, so a checkbox, a hidden input and a submit button are all read-write; and `IsReadOnly` falls through to `return true` for anything that is not an `IHtmlElement`, so an SVG or MathML element is `:read-only` where the standard puts it in neither class. Its editing arm reads `IsContentEditable`, which `Events/ContentEditing` already records as answering false for `contenteditable` written without a value. `ReadWriteStateSelector` owns all three categories, reuses this file's `:disabled` for "not disabled" and `ContentEditing.HostOf` for the editing host, and adds the document's design mode. No upstream issue has been filed |
| `:placeholder-shown` | [HTML §4.16.3](https://html.spec.whatwg.org/multipage/semantics-other.html#selector-placeholder-shown) matches an `input` or a `textarea` whose placeholder is being presented, which §4.10.5.3.10 confines to the seven type states the attribute applies to | 1.8.0's `IsPlaceholderShown` asks any `IHtmlInputElement` for a non-empty placeholder and an empty value, so `<input type=submit placeholder=…>` matches, and it never answers for a `textarea` at all. `PlaceholderShownSelector` adds the applicability test and the second element. No upstream issue has been filed |
| `:indeterminate` | [HTML §4.16.3](https://html.spec.whatwg.org/multipage/semantics-other.html#selector-indeterminate) matches a checkbox whose `indeterminate` IDL attribute is set, a radio button whose [radio button group](https://html.spec.whatwg.org/multipage/input.html#radio-button-group) holds no checked member, and a `progress` element with **no** `value` content attribute | 1.8.0's `IsIndeterminate` has the checkbox rule, reads the `progress` attribute as `String.IsNullOrEmpty` — so `<progress value="">` is indeterminate there and determinate everywhere else — and has no radio-button rule at all, so every unchecked radio in a group with no checked member answered false. `IndeterminateSelector` supplies the group scan (same tree, same form owner, a compatibility caseless `name` match) and reads the `progress` attribute by presence. No upstream issue has been filed |
| `:focus` and `:focus-within` | [HTML §4.16.3](https://html.spec.whatwg.org/multipage/semantics-other.html#selector-focus) matches `:focus` against the element which has the focus, and [Selectors §9.5](https://drafts.csswg.org/selectors-4/#the-focus-within-pseudo) makes `:focus-within` that element together with every element containing it | AngleSharp 1.8.1 adds native form-control focus transitions, but they use its own event bus and `IElement.IsFocused` flag. Jint keeps its script-visible focus model in `Events/FocusController`; neither native focus change replaces that model. `FocusSelector` and `FocusWithinSelector` read that model, and `:focus-within` walks up from the focused element instead of enumerating each candidate's subtree through a LINQ pipeline. No upstream issue has been filed |
| `:active` | [HTML §4.16.3](https://html.spec.whatwg.org/multipage/semantics-other.html#selector-active) matches an element while it is *being activated*, which includes **any element being actively pointed at** — "the user indicates the element using a pointing device while that pointing device is in the 'down' state" — together with its flat-tree ancestors and the labeled control of a `label` that is itself `:active`. Nothing in it excludes a disabled control | 1.8.0's `IsActive()` answers for a hyperlink and nothing else, off an `IElement.IsActive` flag no part of this package sets, so no element matched while a press was in flight. `ActiveSelector` reads `BrowserEventRealm.MousePressTarget` — the element a trusted pointer press landed on, cleared by its release — and walks up from it so the ancestor rule and the label rule share one traversal. | `:checked` | [HTML §4.16.3](https://html.spec.whatwg.org/multipage/semantics-other.html#selector-checked) matches an `input` whose `type` is in the Checkbox or Radio Button state and whose checkedness is true, and an `option` whose selectedness is true — those two elements and nothing else | 1.8.0's `IsChecked()` also answers for the historical `menuitem`, and reads an input's checkedness without asking about its type state, so a control whose `type` attribute is removed stays `:checked` in the Text state it falls back to. `CheckedSelector` is the two categories the standard lists. | `:required` and `:optional` | [HTML §4.16.3](https://html.spec.whatwg.org/multipage/semantics-other.html#selector-required) matches `:required` against an `input` which *is required* and `:optional` against an `input` **to which the `required` attribute applies** and which is not, so §4.10.5.3.4's fifteen type states bound both: an input outside them is in neither class | 1.8.0 reads the attribute wherever it is written, so `<input type=hidden required>` was `:required` and a hidden input without it was `:optional`. `RequiredStateSelector` adds the applicability test and leaves `select` and `textarea`, which the attribute applies to unconditionally, on the presence of it. No upstream issue has been filed |
| `option.selected = true` in a one-choice `select` | [HTML §4.10.10](https://html.spec.whatwg.org/multipage/form-elements.html#dom-option-selected) sets the selectedness, sets the dirtiness, and then makes the element **ask for a reset**, which runs the select's [selectedness setting algorithm](https://html.spec.whatwg.org/multipage/form-elements.html#selectedness-setting-algorithm) — two steps, gated differently: with nothing selected a select with no `multiple` attribute **and a display size of 1** selects its first option that is not disabled, and with two or more selected a select with no `multiple` attribute leaves exactly one selected whatever its display size. The prose says "all but the *last* in tree order", which taken literally makes `options[0].selected = true` a no-op while a later option is selected; upstream's [`select-ask-for-reset.html`](https://github.com/web-platform-tests/wpt/blob/master/html/semantics/forms/the-select-element/select-ask-for-reset.html) selects every option in turn from last to first and requires each write to win, and Chromium 1124 agrees, so the option that *asked* is the one kept and tree order decides only when nobody asked — a form reset restoring markup that carries `selected` more than once | 1.8.0's `IHtmlOptionElement.IsSelected` setter is the first two steps of the IDL setter — it does record the dirtiness — and asks for no reset, so every option of a one-choice `select` could be selected at once while `selectedIndex` stayed where it was. Found by `checked.html`, whose third row was the one it left failing. Worked around: `HTMLOptionElement.selected` is a `hooks` setter (`DomHostHooks.SetOptionSelected`) and `HtmlSelectState` owns the algorithm, the display size and §4.10.10's disabled option — the same display-size rule `:open` reads and the same disabled-option rule `:disabled` reads. No upstream issue has been filed |
| an option inserted into, or removed from, a one-choice `select` | HTML's [option insertion, removing and moving steps](https://html.spec.whatwg.org/multipage/form-elements.html#the-option-element) all run *update an option's nearest ancestor select*, which runs the same selectedness setting algorithm on the select the option left and the one it joined; upstream's [`select-ask-for-reset.html`](https://github.com/web-platform-tests/wpt/blob/master/html/semantics/forms/the-select-element/select-ask-for-reset.html) is two thirds about exactly this | 1.8.0 runs none of them. Measured against Chromium 1124: appending a selected option to a one-choice `select` that already has one answers `true,true` / `selectedIndex=0` where a browser answers `false,true` / `1`, and removing its only selected option answers `false` / `-1` where a browser's step 1 selects the one that is left. The parse is the same trigger, which is why a freshly parsed `select` with no `selected` attribute has `selectedIndex` −1 here (row below). **Not worked around**: the IDL setter is one member the binding can stand in front of, while these are tree mutations nothing in the projected surface passes through, so they need a mutation seam rather than a hook. No upstream issue has been filed |
| the `selected` content attribute changing on an option of a one-choice `select` | HTML sets no dirtiness in the selectedness setting algorithm, so an option the algorithm touched still responds to its `selected` attribute being added or removed; browsers additionally run the algorithm from the attribute change, which HTML's prose does not say | two halves, both AngleSharp's. Its `IsSelected` setter records dirtiness unconditionally and exposes no way to set the selectedness without it, so an option the reset *deselected* stops responding to its attribute; and nothing runs the algorithm when the attribute changes. Measured against Chromium 1124: after `options[1].selected = true` deselects `options[0]`, re-adding `options[0]`'s attribute answers `false,true` / `selectedIndex=1` where a browser answers `true,false` / `0`. An attribute change on an option nothing has written agrees (`false,true` / `1` both ways). **Not worked around**: `setAttribute`/`removeAttribute` are the only two write paths this package can see, and the ARIA-reference row below is why keying on them alone is not a model. No upstream issue has been filed |
